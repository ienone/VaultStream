# VaultStream 系统构想与演进蓝图

## 状态

active

## 定位

本文档描述 VaultStream 的理想产品形态和长期方向，属于概念蓝图，不代表当前代码已经实现，也不承担 API、数据库字段、模型参数或页面组件规范的职责。具体实现应继续拆成独立计划，并以代码、测试和实际界面为事实来源。

## 一、产品愿景

VaultStream 应成为一个自托管的个人知识流系统：它既能接住用户主动分享的内容，也能从用户授权的信息来源中持续探索；既能把文章、社交内容和富媒体可靠存档，也能通过搜索、事件聚合与 Agent 重新组织这些材料。

它不只是收藏夹、阅读器或聊天机器人，而是一条完整闭环：

> 捕获信息，形成可读存档；理解内容，连接相关材料；主动发现变化，在恰当时机帮助用户判断、回顾与行动。

理想体验应围绕五件事展开：

1. **捕获**：从系统分享、Bot、链接、文件、订阅和探索任务接收信息。
2. **归档**：解析内容、保留来源、处理媒体，并选择合适的展示模板。
3. **理解**：支持全文与语义检索、引用定位、主题关系和知识问答。
4. **探索**：从大量来源中去重、聚合、判断价值并追踪事件变化。
5. **行动**：通知用户、加入关注、补充既有存档、生成摘要或受控分发。

## 二、核心原则

### 内容与用户意图优先

用户关心的是“这是什么、为什么保存、以后怎样找到”，而不是解析任务、数据库状态或模型流水线。后台过程应保持可见和可诊断，但不能支配日常界面。

### 模板明确，能力复用

不同内容拥有不同的阅读方式和信息层级。文章、短帖子、图集、对话、视频等不能被压成一种万能条目；它们可以共享媒体、来源、搜索和播放能力，但必须保留清晰的语义边界。

### 证据先于生成

摘要、问答、事件综合和价值判断都应能回到原文、消息、页码或音视频时间点。模型可以帮助理解，但不应把无法验证的推断伪装成事实。

### Agent 增强流程，不吞并流程

Agent 适合理解自然语言、选择工具、查找证据和提出建议；高频操作仍应有直观界面，权限、安全和外部副作用仍由确定性规则控制。

### 增量处理与成本意识

没有变化的内容不应反复清洗、摘要或索引；大量短讯应先去重聚类再交给模型；Agent 只取得完成当前任务所需的上下文。

### 可追踪、可修正、可恢复

用户应知道内容来自哪里、模型做了什么、系统为什么通知或合并。自动判断允许人工修正，重要修改保留历史，外部动作具备确认和审计。

## 三、统一而自然的信息捕获

VaultStream 应逐步支持：

- Android 系统分享，以及适合 Windows、Ubuntu 的桌面快捷入口或浏览器扩展。
- QQ Bot、Telegram Bot 等消息入口，接收链接、转发消息、相册、文件和音视频。
- 应用内粘贴、上传、手动编辑和批量导入。
- RSS、Telegram Channel、平台账号和其他被用户授权的信息源。
- 在缺少稳定订阅或接口时，由 Browser Agent 执行受控探索。

所有入口都进入同一捕获流程，但入口体验不必完全相同。系统首先识别收到的链接、文字、附件、转发关系和用户指令，再决定解析、合并、保存或确认。

Agent 在捕获阶段应成为自然语言助手。例如用户可以说：

- “保存成图文笔记，第二张图做封面。”
- “补充到上周那条事件里，保留转发者评论。”
- “这是播客，生成章节并加入通勤播放队列。”
- “只保留正文和关键图片，不下载原视频。”

明确指令可以直接执行；存在多个合理模板、合并对象或高存储成本时，只询问一个简短而必要的确认问题。Bot 不应只是收链接的管道，而应成为同一 Agent 能力在消息渠道中的轻量入口。

重复判断应综合平台身份、规范化链接、正文与媒体特征。发现重复时，不应简单丢弃：新的转发评论、来源渠道、发布时间和上下文仍可能有价值，应作为新的来源或观点关联到已有内容。

## 四、存档、来源与保留策略

### 不强制僵硬的“原始层—规范化层—派生层”

系统可以在概念上区分三类信息，但不必把它们变成彼此隔绝的物理层：

- **来源证据**：原链接、平台身份、转发上下文、必要快照和原文件。
- **当前内容**：用户实际阅读、检索、编辑和引用的正文、字幕、封面、章节与媒体。
- **可重建智能结果**：摘要、OCR、语音转写、实体、评分和语义索引。

规范化正文、字幕、封面本来就可以同时服务展示和搜索；模型结果也可能经过用户修订后成为长期内容。重点不是属于哪一层，而是能否检索、能否重建、是否由用户修改、需要保留多久，以及删除会造成什么影响。

### 原始内容不默认永久保存

原始数据的价值与成本差异很大，应采用分级策略：

- 普通网页优先长期保留可读正文和关键媒体；原始 HTML 可短期保留、按重要性永久保存，或在稳定解析后清理。
- 图片与 GIF 根据体积、来源稳定性和归档要求决定本地化；保留远端引用时要明确失效风险。
- 视频和音频默认可只保存元数据、封面、字幕或转写；用户要求离线收藏、来源易失或内容价值较高时再保存原媒体。
- PDF、报告和其他文档通常应保留原文件，同时生成可搜索文本与页面预览。
- 主动探索中未被用户采纳的候选只保留轻量信息，避免资讯噪声转化为永久存储负担。

存储设置应直接说明“占用多少、是否可重建、清理会失去什么”，而不是要求用户理解内部层级。

### 版本和人工修订

用户修改过的标题、正文、标签和模板不能被重新解析静默覆盖。重新抓取或重新识别应产生可比较的新结果，让用户接受、合并或保持现状。来源删除不应自动删除本地归档；本地删除则应区分可恢复删除、缓存清理和不可逆擦除。

## 五、内容模板体系

模板决定列表预览、详情结构、搜索切片和主要操作。以下类别可以共享基础能力，但不应合并成一种“帖子/媒体条目”。

### 文章

用于新闻、博客、专栏、教程和长回答。核心是连续阅读、标题层级、目录、引用、代码、脚注和阅读进度。大屏应限制正文宽度，并把目录、来源和关联内容放入辅助区域。

### 图文笔记

用于图片与分段文字共同完成叙事的攻略、测评、旅行记录和教程。文字与图片的对应关系是主体，适合图文交错、步骤、地点或对象卡片；它不是“几张图片加一段说明”的图集。

### 短帖子

用于单条微博、动态、短评和带社交上下文的转发。重点是作者、时间、平台来源、引用关系和转发者评论，详情保持紧凑，不套用文章目录和长文排版。

### 帖子串

用于连续推文、楼层串、连续更新或回复链。重点是顺序、父子关系、作者变化和逐条来源定位，以纵向消息链阅读，而不是拼成一篇失去边界的长文。

### 图集

用于图片、GIF 或短片段本身就是主体的内容。主要体验是网格、沉浸浏览、排序、单项说明、原图信息和媒体操作；社交平台文字只是来源或补充。

### 对话与消息包

用于聊天记录、Telegram 多条转发和多发送者消息。需要保留发送者、时间、回复、引用、附件和消息编号，并允许按单条消息检索和引用。

### 视频

视频本体、音轨、字幕、章节、封面、简介和来源共同构成内容。字幕和转写可全文检索，引用应落到具体时间点。视频详情的核心是观看、章节导航、字幕与相关资料。

### 音频与播客

音轨是主体，围绕节目、作者、封面、章节、逐字稿、Show Notes、播放队列、倍速、定时停止、书签和时间点笔记组织。它应拥有完整而漂亮的播放器体验，而不是普通附件卡片。

### 文档

用于 PDF、报告、幻灯片和扫描材料。保留原文件、页码和版面关系，同时提供目录、文本层、OCR 和页面预览；搜索与 Agent 引用应能定位到页码或区域。

### 书签

用于暂时不需要深度解析、解析失败或只想记录“为什么保存”的链接。它是轻量而明确的类型，可以以后升级成其他模板，但不应成为所有未知内容的永久垃圾桶。

模板判断以内容的主要消费方式为准：微博配九图可能是短帖子，也可能是图集；小红书攻略通常更接近图文笔记；视频动态应以视频为主体，原帖作为来源；Telegram 多条转发则根据回复关系选择帖子串或消息包。自动判断必须允许用户修正。

## 六、富媒体与全局播放体验

音频与视频需要不同的详情模板，但共享一个跨页面的播放会话。离开详情页后播放不应中断：

- 音频收纳为全局迷你播放器，并继续后台播放。
- 视频可以缩为应用内迷你播放器或进入系统画中画。
- 用户可以把视频切换为仅播放声音，保持进度、章节和队列。
- 返回详情页时重新展开同一播放会话，而不是创建第二个播放器。

Android 应接入原生媒体会话和通知，支持锁屏控制、耳机与蓝牙按键、音频焦点、后台恢复和视频画中画。其他平台再逐步接入各自的系统媒体控制。

播放器必须同时考虑横竖屏：手机竖屏以画面或封面、主控制和章节为主；手机横屏优先媒体本体，在空间允许时显示字幕或队列；平板和桌面使用播放器与字幕、章节、资料的双栏布局。布局应依据实际宽高和折叠区域，而不只是简单判断屏幕方向。

富媒体检索以字幕、转写、章节、说明、OCR 和必要的视觉理解结果为入口。视频、音频和图片的模型描述必须标明是生成内容，不能冒充来源事实。

## 七、搜索、RAG 与知识组织

搜索应同时支持精确字段、全文、语义和结构化筛选，并允许沿人物、主题、来源、引用、重复、版本和事件关系继续浏览。收藏库首先返回真实内容和匹配片段，RAG 是可展开的增强，而不是用一段聊天答案替代搜索结果。

不同模板需要不同的检索粒度：文章按章节和段落，帖子串与对话按消息节点，音视频按章节和时间范围，文档按页码和版面。无论采用何种检索方案，结果都必须带回内容版本和可定位证据。

RAG 的可靠性来自混合召回、权限过滤、适度重排、受限上下文和固定评估集，而不是单纯更换向量数据库。开源解析、OCR、语音识别、全文搜索和向量方案应另做专项调研，用中文内容、现有数据量、设备资源和维护成本进行比较，不在本概念文档提前定案。

## 八、主动探索与信息过载治理

主动探索的目标不是抓得更多，而是让用户更少重复阅读，同时不错过高价值和高时效信息。

接入顺序应优先选择稳定、低成本的 RSS 与公开接口，再考虑平台轮询，最后才使用 Browser Agent。系统先做链接、平台身份和内容特征去重，再进行主题与事件聚类；只有难以确定的近似关系、价值判断和综合解释才交给模型。

价值判断不能只模仿推荐系统的点击率。它应结合时效性、信息密度、来源可信度、与用户兴趣和知识库的关系、新颖度、可行动性以及用户历史反馈。判断结果用于排序、聚类、通知分级和内部诊断；日常动态不展示分数、“为什么推荐”或模型式可信说明。用户仍应能降低来源权重、关闭主题或纠正判断。

高频快报适合先形成批次摘要或事件更新；普通更新进入动态流；高时效、高相关且高置信的内容才立即通知。系统应学习“哪些提醒有用”，但不能把用户画像变成不可解释的黑箱。

## 九、事件聚合

事件不是新的内容模板，而是跨模板的组织视图。它把围绕同一现实对象或持续话题的文章、短帖子、帖子串、图集、对话、视频、音频和文档联系起来，同时保留每个成员自己的阅读方式。

一个事件页面应包含：

- 简洁标题和当前状态。
- 按时间排列的关键进展，而不是所有抓取记录。
- 作为原始来源、独立报道、评论观点、背景资料或更正信息加入的内容。
- 已确认事实、尚未确认的信息和彼此冲突的观点。
- 与资料库中历史事件、人物和主题的关系。
- 用户关注原因、最近变化和下一步值得观察的问题。

Agent 可以根据新成员增量更新事件综合，但必须逐条引用证据。纯重复内容只增加来源可信度，不重复占据时间线；带有新评论的转发既关联原始内容，也保留评论者观点；图集和视频可以成为现场证据，播客和长文可以作为分析，聊天消息则可能是线索而非已确认事实。

事件的自动合并和拆分必须可撤销。置信度不足时只提出建议；用户确认过的边界应成为后续判断的重要依据。

## 十、Agent 的角色与能力

Agent 不应只存在于一个独立聊天页，而应作为跨场景能力出现：

- 在分享和 Bot 中理解保存、模板、合并和媒体保留指令。
- 在收藏库中搜索、比较、解释和生成带引用的回答。
- 在内容详情中补充背景、提取结构、生成笔记或提出关联。
- 在事件页中寻找原始来源、比较观点并更新综合。
- 在自动化中解释失败、提出修复步骤和创建规则草案。

复杂任务需要展示目标、正在使用的工具、证据、待确认动作、运行状态和结果。只读查询可以顺畅执行；本地可撤销修改可以按策略自动执行；高成本调用、外部发送、账号操作和危险配置必须确认。

长期记忆应主要来自结构化偏好、用户反馈和可引用资料，而不是无限注入历史聊天。知识事实来自存档证据，模型过去说过的话不能自动成为事实。

## 十一、模型调用与 token 成本

清洗、分类、评分、摘要、语义索引和 Agent 应通过统一的模型调用层协调，而不是各自拼接提示、各自重试和各自记录成本。该层负责选择模型、复用结果、组织上下文、记录调用和执行隐私策略。

节约成本的主要方式包括：

- 确定性解析、规范化和哈希去重先于模型。
- 内容未变化时复用已有摘要、分类和语义索引。
- 高频短讯先聚类，再按簇进行摘要和价值判断。
- 简单任务使用规则或小模型，复杂任务才升级到强模型。
- 长内容先索引，Agent 按需取得片段，不反复注入全文。
- 事件只根据新增或变化的成员更新受影响部分。

供应商侧 Prompt Cache 需要从提示结构上主动设计：稳定的系统说明、策略和工具定义保持一致并放在前部，变化的内容和当前上下文放在后部，避免随机信息破坏前缀一致性。供应商返回的缓存 token 和命中信息应被真实记录，而不是用本地缓存概念代替。

日常主界面不展示 token 预算。设置与诊断页面提供结构化调用日志，可按时间、场景、模型、供应商、缓存状态、费用、延迟和错误筛选，帮助发现重复调用和高成本流程。

## 十二、界面形态与 Material 3 Expressive

主导航应保持少而清晰：

- **动态**：回答“现在值得看什么”，承载订阅更新、事件变化和摘要。
- **收藏库**：回答“保存了什么、如何找到和消费”，承载搜索、阅读和播放。
- **自动化**：回答“系统正在做什么、为什么失败、怎样控制”，承载捕获、同步、解析、索引和分发任务。

搜索与 Agent、通知、设置和当前播放会话属于全局能力。Agent 可以有复杂任务工作台，但不必强占主导航。

Material 3 Expressive 应用于信息层级、对象关系、状态和有目的的动效，而不是大量彩色胶囊、边框和“SVG 图标加文字”的重复组件。一个区域只保留一个明确主操作；不直观的图标必须有文字、提示或菜单说明；低频动作进入菜单或详情层。

项目需要自己的统一形状、间距、颜色、字阶和动效规范。在不破坏可访问性和状态表达的前提下，可以对选择框、菜单和表单建立更圆润的视觉语言，而不是被默认直角组件束缚。

自适应布局应按可用空间变化：手机以单列和底部导航为主；中等宽度使用导航栏和可切换双栏；大屏使用列表—详情和辅助面板；超宽窗口限制正文与表单宽度。手机横屏还要检查高度，折叠屏避开铰链。深层页面应支持预测性返回、状态恢复和连续的列表到详情转场。

性能是设计的一部分：长列表分页和懒加载，媒体使用低成本预览，后台转码不阻塞首屏，播放器、搜索状态和长任务不依附单个页面生命周期。Animeko 作为长期参考仓库，应持续提取其导航、响应式布局、状态组织和 Material 界面经验，但不直接复制实现。

## 十三、自动化、通知与分发

所有长任务应以一致方式展示状态、阶段、进度、触发来源、关联内容、失败原因以及是否可取消、重试或恢复。可恢复的临时错误由系统处理；需要用户修复账号或配置时，界面应说明根因和下一步，而不是只给出“失败”。

通知至少区分：需要立即注意的高时效信息、账号或任务异常、周期摘要、用户主动任务完成，以及只记录不打扰的静默状态。通知支持去重、合并、静默时段和过期，Agent 只能在用户策略内建议关注或发送提醒。

归档与分发必须解耦。保存内容不等于自动外发；分发规则根据主题、标签、来源、风险和目标决定是否进入队列，并保留渲染、确认和结果记录。

## 十四、账号、隐私与扩展性

VaultStream 首先服务单人自托管，不应过早堆叠多租户管理界面，但数据、凭据、任务、搜索索引和 Agent 权限要能自然扩展到用户与工作空间。

系统需要区分 VaultStream 用户、外部平台账号以及 Bot/通知身份。凭据加密保存，不进入普通日志、模型上下文或可随意导出的配置。已连接账号、平台身份、登录状态、权限和修复动作由独立账号中心集中管理；设置只管理应用与系统配置，其他页面只显示必要状态并跳转账号中心。

平台解析、存储、搜索、模型、通知分发和 Agent 工具都应是清晰的扩展点，并拥有固定样本和契约测试。扩展性意味着边界稳定，而不是长期保留多个旧实现和运行时猜测。

## 十五、后端与 Rust 远景

近期继续以 FastAPI/Python 作为模块化单体，利用其业务编排、AI 和文档处理生态。优先收敛模块职责、数据契约、任务边界和测试，不提前全面重写。

当真实性能数据证明有必要时，Rust 可以承担高并发下载、媒体校验与处理、大规模去重、独立全文索引或高吞吐任务执行等稳定能力。快速变化的平台逻辑和模型编排可以继续留在 Python。

迁移应从一个边界清晰的 worker 或 sidecar 开始，用同一批样本和负载比较资源、延迟和维护成本；确认收益后删除旧路径，不让 Python 与 Rust 双实现无限并存。

## 十六、实施路线

本文只定义理想产品形态，不再维护独立的开发阶段顺序。阶段优先级、前置依赖、当前第一批次和专项计划队列统一以 `./2026-07-17-vaultstream-development-roadmap.plan.md` 为准。

任何具体领域开始实现前，都应从总路线进入相应专项计划，并按可独立验收的垂直切片推进；不能把本蓝图直接交给 Agent 一次性实现。

## 十七、理想状态的判断标准

- 用户从手机分享或向 Bot 转发后，可以自然说明如何保存，并迅速得到可读结果。
- 同一资讯从多个来源进入时不会反复占据注意力，同时保留有价值的评论和观点差异。
- 文章、图文笔记、短帖子、帖子串、图集、对话、音频、视频和文档都有适合自身的稳定展示。
- 音视频离开详情仍能播放，支持横竖屏、仅音频、画中画和 Android 原生媒体控制。
- 搜索既能精确找到内容，也能按语义和关系探索；Agent 回答可以定位原文、页码或时间点。
- 主动探索先去重和聚类，再使用模型；动态流不暴露内部评分或推荐解释，只有重要变化才通知。
- 事件页能区分事实、未确认信息和观点分歧，并通过新证据增量更新。
- 模型调用日志能真实反映供应商缓存、费用和重复计算，日常界面不被 token 指标淹没。
- 核心页面在手机竖屏、横屏、平板和桌面上都清晰、流畅、可返回、可恢复。
- 系统扩展新平台、账号或高性能组件时不需要破坏已有内容和用户路径。

## 主要风险

- 模板和内容模型重构触及既有数据，需要迁移、回滚和真实样本验证。
- 富媒体后台播放与系统媒体控制需要平台原型，不能只靠插件清单决定。
- 平台抓取受认证、接口变化、反爬和平台条款影响。
- 事件聚合和价值判断可能错误关联，必须保留证据和人工修正。
- 媒体归档、模型调用和主动探索都可能迅速扩大资源消耗，需要克制默认值。
- 过早多租户化、微服务化或 Rust 重写会分散对核心使用体验的修复。
- 再次交由 Agent 无监督大规模推进，会重现界面、文档和实现同时失控的问题。
