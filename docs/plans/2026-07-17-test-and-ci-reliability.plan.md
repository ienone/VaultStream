## 背景

VaultStream 已有大量后端和 Flutter 测试，但数量和覆盖率不能等同于成熟保障。当前套件存在价值密度不均、准备代码重复、实现细节绑定、运行偏慢和资源警告；本地与 GitHub Actions 还曾对同一后端测试给出不同结果。

## 目标

- 以用户流程、数据不变量、安全边界和历史高风险缺陷决定测试投入。
- 明确单元、契约、集成、端到端、平台探针和人工验收的职责。
- 让本地、CI 和部署使用可复现的依赖基线。
- 缩短日常反馈时间，同时保留关键失败路径、权限、幂等性、并发和数据一致性保障。
- 建立测试新增、合并、删除和长期维护规则。

## 非目标

- 不以测试数量、覆盖率或快照数量作为完成标准。
- 不把真实平台账号、Cookie、外部网络和付费模型调用放入默认 CI。
- 不为脆弱测试冻结合理内部重构。
- 不重新启用普通 push 自动触发。
- 不在本计划中实现业务功能。

## 变更范围

- `backend/tests/`、`frontend/test/` 和必要的端到端验收入口。

- 代表性数据、媒体样本、RAG 评估集和手工平台探针边界。
- 测试规范、耗时/不稳定性记录和维护制度。

## 建设原则

### 从风险出发

首批风险包括内容丢失或重复、用户修订被覆盖、迁移和清理造成数据损失、自动化与 Agent 绕过策略、外部分发重复执行、证据无法定位以及核心页面无法完成任务。

### 测试层级各自负责

- 单元测试：复杂纯逻辑、去重、策略和状态机。
- API/协议契约测试：输入输出、状态码、错误和事件语义。
- 数据与任务集成测试：事务、迁移、队列、幂等性、并发和恢复。
- Flutter controller/provider 测试：动作编排、状态、错误和路由结果。
- Widget 与自适应测试：关键任务、失败态、断点结构和可访问性。
- 少量端到端冒烟测试：捕获到存档、搜索到证据、失败到恢复。
- 真实平台探针：只在 `backend/manual_tests/` 或受控人工环境运行。

### 测试必须可维护

重要测试应能说明其保护的用户行为或不变量。只验证框架默认行为、重复 mock、私有实现顺序或无业务差异输入的测试，应合并、改写或删除。删除时记录替代保障，不建立长期隔离区。

## 实施阶段

1. 建立风险—测试映射，列出核心流程、数据不变量和历史故障。
2. 采集耗时、重复 fixture、资源警告、不稳定结果和外部依赖。
3. 建立 Python 依赖约束或锁定与更新流程，并在干净 Windows/Linux 环境验证。
4. 收敛后端测试，优先稳定 API contract、策略、迁移、任务和适配器边界。
5. 收敛 Flutter 测试，补 controller/provider、关键 widget 和多断点验收。
6. 建立使用代表性样本、但不访问真实外部平台的最小端到端链路。
7. 调整 Quality Gates，让测试、安全、文档、schema 和敏感信息检查分别给出结果。
8. 建立慢测试、重复测试、脆弱测试和新缺陷回归测试的持续维护规则。
9. 对少量关键领域进行变异测试或故障注入抽查。

## 验收标准

- 核心用户流程和高风险不变量有明确的自动化或人工验收责任。
- 默认测试不访问真实网络、平台账号或付费模型。
- 本地和 CI 从同一依赖基线安装后结果可重复。
- 默认反馈时间有明确预算，慢速测试进入恰当层级。
- 测试数量可以下降，但关键缺陷和数据一致性保障不得下降。
- Flutter 核心页面具有手机竖屏、横屏、平板和桌面验收证据。
- 各类质量门能分别报告结果。

## 风险

- 未建立风险映射前删测试可能误删唯一保护。
- 依赖锁定若脱离部署环境，只会让 CI 表面稳定。
- 过多端到端和视觉快照会重新造成慢和脆弱。
- 真实平台变化仍需要受控探针与人工复核。
- 没有持续规则时，测试治理会退化为一次性清理。
