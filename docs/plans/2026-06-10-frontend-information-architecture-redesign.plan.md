# 前端信息架构与自适应 UI 重设计规划

## 状态

active

## 背景

当前前端已经具备收藏库、动态页、收件箱、自动化、账号中心、设置、任务结果等页面，但页面职责与理想产品形态仍不一致。新的产品定位应从“后台管理式页面集合”转向“个人信息聚合、归档、浏览、收藏、自动化转发系统”：

- 动态页应成为 AI 辅助的信息流浏览页，而不是鸡肋的今日工作台或系统仪表盘。
- 原收件箱的“候选内容审核”心智不适合个人自用场景，应融入动态信息流。
- 任务结果、失败、撤销和中止更适合进入通知中心，而不是作为常驻工具入口。
- 收藏库当前形态相对接近目标，应重点优化 UI/UX、筛选形态、媒体支持、卡片到正文转场和未来 RAG 搜索。
- 自动化页是重要主页面，但必须通过概览、分区、下钻列表进行断舍离，避免继续膨胀。
- 账号中心作为独立入口过重，更适合作为设置中的强子页。
- Agent/RAG 暂不作为主设计对象，待动态、收藏库、自动化、通知中心和设置体系稳定后再扩展。
- 前端整体应学习 Gmail / Material adaptive 的导航、动效、预测性返回、Snackbar undo、list-detail 和性能策略。

## 目标

1. 建立新的主信息架构：动态、收藏库、自动化作为主入口；通知中心和设置作为工具入口；收件箱与账号中心降级或并入其他页面。
2. 明确动态页的新定位：以订阅源、AI 推荐、发现内容和同步摘要组成个人动态信息流。
3. 设计通知中心：统一承载运行中任务、失败通知、最近完成、任务详情入口、中止入口和部分撤销入口。
4. 保留并强化收藏库：优化筛选形态、搜索/RAG 入口、卡片到正文无缝转场、音频/视频/多媒体详情支持。
5. 重构自动化页的信息层级：收藏同步、分发、解析/后处理三大域，首页只展示概览、异常和入口，具体列表下钻。
6. 将账号中心收敛为设置中的“账号与平台”强子页。
7. 定义 Root Shell、Section Shell、Detail Shell 三种页面外壳，解决深层页面仍挂在常驻侧边栏/底部栏下的生硬问题。
8. 建立统一重试、撤销和中止设计原则。
9. 给后续实现拆分提供分阶段步骤和验收标准。

## 非目标

- 本计划不直接修复当前代码问题。
- 本计划不立即实现 Agent/RAG 工作台；RAG 只作为收藏库搜索增强的未来方向记录。
- 本计划不重写后端平台适配器、解析器、同步任务或分发 worker。
- 本计划不要求一次性删除所有旧路由；实施阶段可根据风险决定是否短期保留 redirect，但最终不保留重复页面职责。
- 本计划不把每个 UI 细节写成视觉稿；具体 token、组件样式和动效参数应在实施计划或组件文档中继续细化。

## 核心信息架构

### 主入口

主导航只保留三个高频业务入口：

```diagram
╭────────╮   ╭────────╮   ╭────────╮
│ 动态   │   │ 收藏库 │   │ 自动化 │
╰────────╯   ╰────────╯   ╰────────╯
```

- 动态：订阅源、AI 推荐、发现内容、同步摘要组成的信息流。
- 收藏库：已保存内容的浏览、搜索、筛选、阅读、管理和未来 RAG 检索。
- 自动化：收藏同步、分发、解析/后处理的概览与控制。

### 工具入口

工具入口不作为主业务导航：

- 通知中心：右上角按钮或移动端顶部操作，承载任务和系统通知。
- 设置：右上角/工具入口进入，采用 Section Shell。
- 搜索：可在动态和收藏库内上下文展示，必要时全局入口打开统一搜索。
- Agent/RAG：暂缓，不进入当前主导航。

### 降级或并入

- 收件箱：不再作为主页面；候选浏览、AI 推荐、收藏/忽略/稍后操作并入动态信息流。
- 账号中心：不再作为独立主工具入口；收敛到设置中的“账号与平台”强子页。
- 任务结果：不作为工具入口；由通知中心、自动化、详情页动作跳转到 `/tasks/:runId`。

## 页面设计规划

### 页面设计总原则

页面规划应以用户任务和内容生命周期组织，而不是以当前代码模块或后端 router 组织。所有页面都要回答三个问题：用户来到这里是为了看什么、决定什么、执行什么。

- 主入口页面只承担高频主任务，避免继续堆系统状态、设置项和后台日志。
- 二级管理页面使用 Section Shell 表达“列表/导航 + 当前内容”的关系。
- 深层详情页面使用 Detail Shell 整页进入，避免在常驻主导航下继续叠加复杂内容。
- 任务状态、失败、撤销和中止不散落在各个页面，而由通知中心和任务详情页统一承载。
- 动效只表达对象关系和层级变化，例如卡片到正文、列表项到详情、图片到全屏；不为装饰而动。

### 动态页：AI 辅助信息流

动态页应成为用户每天打开产品时首先浏览的信息流，而不是“今日工作台 / 系统仪表盘”。它的核心任务是把接入平台的订阅内容、发现内容和 AI 推荐内容按用户需要排序、摘要并呈现。

#### 页面定位

- 展示新的、可能值得看的内容。
- 帮助用户快速判断是否收藏、稍后、忽略或打开原文。
- 支持按时间线、AI 评分、综合推荐、平台/来源筛选浏览。
- 以 digest 方式提示收藏同步新增，而不是把同步结果逐条刷屏。

#### 信息来源与 item 类型

动态流至少区分三类 item：

1. 内容 item：来自订阅源、发现源、AI 推荐或手动接入链接，代表一条可阅读内容。
2. Digest item：代表一次批量事件的摘要，例如收藏同步新增、某平台订阅更新汇总。
3. 轻提示 item：低干扰提示，例如“某来源近期质量下降”“该平台登录即将过期”，但严重失败应进入通知中心。

内容 item 的基本字段：

- 来源平台、来源名称、作者、发布时间或抓取时间。
- 标题、封面或 fallback、内容类型。
- AI 摘要、AI 评分、推荐理由、主题标签。
- 当前状态：未读、已收藏、稍后、已忽略、已归档。
- 操作：收藏、稍后、忽略、打开原文、进入详情。

Digest item 的基本字段：

- 事件来源，例如“知乎收藏同步”“Bilibili 订阅更新”。
- 新增、重复、失败、跳过等聚合数字。
- 主操作：查看新增、查看任务、进入收藏库筛选结果。

#### 桌面布局

桌面优先采用 list-detail：

```diagram
╭────────────────────────────────────────────╮
│ 顶部：动态标题 / 搜索 / 排序 / 筛选 / 通知   │
╰────────────────────────────────────────────╯
╭──────────────────────╮ ╭──────────────────╮
│ 信息流列表             │ │ 当前选中内容预览   │
│ 时间线 / 推荐 / 高分    │ │ 摘要、正文片段      │
│ Feed card / Digest     │ │ 操作和原文入口      │
╰──────────────────────╯ ╰──────────────────╯
```

- 左侧信息流保留滚动位置和选中项。
- 右侧预览用于快速阅读 AI 摘要、正文片段、媒体缩略图和主要操作。
- 宽度不足时右侧预览收起，点击 item 进入 Detail Shell。

#### 移动布局

- 单列信息流。
- 顶部保留搜索、筛选和通知中心入口。
- 底部主导航只保留动态、收藏库、自动化。
- 点击内容进入全屏详情；返回时恢复原滚动位置。

#### 收藏同步内容呈现

- 其他平台已收藏内容默认进入收藏库，因为用户已经在外部平台表达过兴趣。
- 动态页只展示低频 digest，例如“知乎收藏同步完成：新增 23 条，重复 12 条，失败 1 条”。
- 点击 digest 的“查看新增”应进入收藏库并带明确过滤条件。
- 同步失败、登录失效、任务异常进入通知中心。
- 重复、跳过等低价值信息只进入任务详情，不主动打扰。

#### 不承担职责

- 不展示完整后台任务 JSON。
- 不承担完整收藏同步历史。
- 不承担账号修复主流程。
- 不承担分发规则编辑。

#### 状态与空态

- 初次使用时解释需要配置订阅源、发现源或收藏同步。
- 加载失败时区分后端不可用、源不可用、空结果。
- 筛选无结果时提供清空筛选和调整排序入口。

### 收件箱能力并入动态页

原收件箱的“候选内容审核页”心智不适合个人自用的信息聚合产品。相关能力应作为动态流的一部分存在。

能力迁移关系：

| 原收件箱能力 | 新位置 |
|---|---|
| 候选列表 | 动态信息流 |
| AI 评分 | 动态卡片评分和排序 |
| AI 分析理由 | 动态详情预览 |
| 收藏 | 动态 item 主操作 |
| 忽略 | 动态 item 主操作 |
| 稍后处理 | 动态 item 主操作 |
| 批量处理 | 动态选择模式，默认不作为首屏能力 |
| 发现源筛选 | 动态筛选 |
| 候选详情 | 动态详情 / 右侧预览 |

旧 `/inbox`、`/discovery` 路由在实施时可以短期保留 redirect 或作为内部筛选视图，但不再作为主导航入口，也不再承担“审核后供他人浏览”的产品语义。

### 收藏库：稳定核心资产页

收藏库是产品的资产库，应尽量保留当前已经较完善的核心体验，再围绕阅读、搜索、筛选、媒体和转场做增强。

#### 页面定位

- 浏览、搜索、筛选和管理已保存内容。
- 支持从同步、动态、手动保存等来源进入的内容统一沉淀。
- 承担收藏域内批量操作和内容详情入口。

#### 布局与筛选

筛选使用响应式三态策略，而不是固定常驻或完全弹窗二选一：

- 手机：搜索栏 + 筛选按钮，筛选通过 bottom sheet 展示。
- 中等宽度：顶部筛选 chips 展示当前筛选摘要，点击展开筛选面板。
- 宽屏：默认仍以内容为主，允许用户 pin 住左侧筛选栏；pin 状态应可记忆。

筛选项包括平台、标签、作者、状态、日期、内容类型、是否 NSFW、语义搜索参数等。筛选状态应能通过 route query 或明确状态恢复，避免其他页面直接写收藏页 provider。

#### 卡片与详情

- 卡片继续作为内容摘要：平台、标题、作者、封面/fallback、摘要、标签、状态。
- 卡片上不堆大量动作；高频操作是点击进入详情和选择模式批量操作。
- 卡片到正文使用 container transform，源端是卡片容器，目标端是详情阅读 surface；正文和侧栏在容器展开后再出现。
- 内容详情支持文章、图集、视频、音频、用户资料等类型，并在不同内容类型下选择适合的阅读/播放布局。

#### 搜索与 RAG

RAG 不作为独立 Agent 页面优先实现，而应先融入收藏库搜索：

- 关键词搜索：准确查找标题、作者、正文、标签。
- 语义搜索：按意思找内容。
- 未来 RAG 搜索：自然语言问题 + 结果摘要 + 引用内容列表。

搜索结果页应展示匹配内容、AI 汇总、引用段落、来源和相关标签，而不是只返回聊天式答案。

#### 性能与状态

- 瀑布流需要稳定滚动性能和图片缓存。
- 返回详情后保留列表滚动位置。
- 批量操作应明确进入选择模式，不在普通浏览态干扰卡片。

### 自动化：概览 + 三大域 + 下钻列表

自动化页保留为主入口，但必须从“大杂烩控制台”收敛为“自动运行能力的概览和入口”。一级页面只展示状态概览、异常摘要和三个业务域入口：收藏同步、分发、解析/后处理。

```diagram
╭────────────────────────────────────────────╮
│ 自动化总览：运行中 2 · 失败 1 · 暂停 0       │
╰────────────────────────────────────────────╯
╭────────────╮ ╭────────────╮ ╭──────────────╮
│ 收藏同步   │ │ 分发       │ │ 解析/后处理  │
│ 摘要 + 入口 │ │ 摘要 + 入口 │ │ 摘要 + 入口   │
╰────────────╯ ╰────────────╯ ╰──────────────╯
╭────────────────────────────────────────────╮
│ 需要处理：登录失效 / 分发失败 / 解析失败      │
╰────────────────────────────────────────────╯
```

#### 自动化总览

总览只展示：

- 当前运行任务数量和主要任务类型。
- 失败任务数量和最高优先级问题。
- 策略暂停或用户禁用状态。
- 三大域摘要卡。
- 最近需要处理事项，点击进入通知中心、任务详情或对应子域。

总览不展示完整历史列表、所有平台卡片、所有失败项或复杂配置表单。

#### 收藏同步域

一级展示：

- 启用平台数、认证可用平台数、当前是否正在同步。
- 最近一次同步摘要：新增、重复、失败、耗时。
- 需要处理：登录失效、平台不可用、失败项数量。
- 主操作：同步全部、同步单平台、查看历史、查看失败。

二级/下钻展示：

- 平台列表：平台状态、认证、速率、最近同步。
- 历史 run 列表：按时间展示结果摘要。
- 失败项列表：只在需要处理时展示，支持查看原因。
- 重试：仅当用户修复了根因后出现，例如重新登录后重试该平台。

不展示：

- 未实现 placeholder 策略。
- 每条历史 run 的完整 JSON。
- 对所有失败项默认铺开重试按钮。

#### 分发域

一级展示：

- 待分发、已过滤、已分发、失败计数。
- 当前队列摘要和最近失败目标。
- 规则数量和规则健康状态。
- 主操作：进入队列、进入规则、查看历史。

二级/下钻展示：

- 分发队列：待推送、已过滤、已推送列表。
- 规则列表：规则启用状态、命中摘要、目标摘要。
- 规则详情：编辑标签匹配、NSFW、频率限制、目标和审批策略。
- 分发历史：按目标和内容追踪结果。

重试原则：推送失败只在目标配置、网络或权限问题修复后显示明确重试；已发送的外部消息默认不可撤销。

#### 解析 / 后处理域

一级展示：

- 解析成功率、失败数量、主要失败平台。
- 媒体归档状态。
- 语义索引状态。
- 最近失败任务和修复建议。

二级/下钻展示：

- 解析历史。
- 失败内容列表。
- 媒体归档任务和失败媒体。
- 语义索引/embedding 任务。
- 后处理任务详情。

显式重试只在失败原因具有可恢复性时展示。若平台解析器不可用或内容格式不支持，前端应显示原因和等待修复，而不是鼓励用户反复点击重试。

#### 批量操作层级

- 一级概览不提供批量操作。
- 列表下钻页进入选择模式后才展示批量动作。
- 批量动作执行后通过通知中心展示运行进度和中止入口。

### 通知中心：任务、失败、中止和撤销入口

通知中心不是主导航页面，而是顶部工具入口。它统一承载系统状态、任务进度、失败处理和最近完成结果。

#### 入口与布局

- 桌面：顶部工具按钮打开侧边抽屉、弹出面板或 Section Shell 下钻页面；未读/待处理数量用 badge 提示。
- 移动：顶部右侧按钮进入全屏通知中心。
- 通知中心本身可继续下钻到任务详情 `/tasks/:runId` 或业务页面。

#### 信息分组

通知中心按处理优先级分组：

1. 正在运行：收藏同步、媒体归档、批量解析、分发任务等。
2. 需要处理：登录失效、同步失败、解析失败、推送目标异常、策略阻止。
3. 最近完成：最近完成的同步、分发、解析、索引任务摘要。
4. 历史入口：进入完整任务历史或按类型筛选历史。

#### 通知 item 结构

每条通知至少包含：

- 类型：running、attention、completed、undoable。
- 标题和短描述。
- 来源模块：同步、分发、解析、账号、媒体、搜索等。
- 时间和状态。
- 主操作：查看详情、修复、打开相关页面、中止、撤销。
- 可选 run id、关联内容 id、平台 id。

#### 中止与撤销

- 长任务状态不依赖长时效 toast；toast 只用于即时反馈。
- 可中止任务在通知中心“正在运行”分组显示中止按钮。
- 相关业务页面也可以显示局部中止入口，但通知中心是全局兜底入口。
- 撤销仍优先通过 Snackbar，例如“已删除 1 条收藏 [撤销]”；通知中心可以保留最近可恢复操作记录，但不替代 Snackbar。

### 任务详情页：通知中心与自动化的详情落点

`/tasks/:runId` 不作为主导航入口，而是通知中心、自动化、内容详情等页面跳转的统一详情页。

页面结构：

- 顶部状态头：任务类型、状态、run id、开始/结束时间。
- 结构化摘要：平台、触发来源、影响对象、成功/失败计数。
- 业务 renderer：按 task type 展示同步结果、分发结果、解析结果、媒体归档结果等。
- 可操作区：只有在任务可取消、可修复后重试或可跳转关联对象时展示。
- 调试 payload：metadata/result JSON 默认折叠，供排查问题时展开。

任务详情页要替代动态页底部 run 弹层和收藏同步面板 run 弹窗，避免同一 run 多处重复展示。

### 设置：Section Shell + 账号与平台强子页

设置页采用独立 Section Shell，不作为 Root Shell 内普通 tab。桌面端采用左侧设置列表 / 二级导航、右侧内容区域的分层布局：

```diagram
╭──────────────╮ ╭────────────────────────────╮
│ 设置列表      │ │ 当前设置内容区域              │
│ 二级导航      │ │ surface / 表单 / 媒体 / 详情  │
╰──────────────╯ ╰────────────────────────────╯
```

UI 思路：

- 这里的核心约束不是“左侧必须黑色、右侧必须灰底圆角”，而是左侧导航区和右侧内容区必须形成清晰的主次、选中和层级关系。
- 左侧可以使用黑色 / 深色 / 高对比背景、选中胶囊、分组标题或细分隔线来表达二级导航；具体色彩应服从页面整体主题和内容类型。
- 右侧内容区可以使用灰色背景 + 圆角内容 surface、分组卡片、全幅媒体 / Hero 头图、沉浸式详情或其他 Material surface 表达；选择依据是当前内容的阅读/配置/媒体属性。
- 灰色背景上的圆角内容 surface 是设置、表单、管理类页面的推荐表达之一，但不是所有 Section Shell 的强制样式。
- 无论采用哪种表达，右侧都必须让用户明确感知“当前正在编辑/查看的是哪一项”，并避免导航区、背景区和内容区混成同一平面。
- 左右比例可拖动调整；默认左栏固定在约 240-320px 范围，右侧自适应。
- 竖屏下收折为设置列表；点击某项进入全屏详情，左上角返回。

设置分区：

#### 账号与平台

账号与平台是设置中的强子页，用于替代独立账号中心：

- 平台卡片展示连接状态、Cookie 状态、登录检测、收藏同步认证摘要。
- 主操作包括连接、重新连接、检测、解绑。
- 平台异常应给出修复建议，例如登录失效、Cookie 缺失、同步认证失败。
- 收藏同步只展示认证摘要和跳转自动化收藏同步域，不在这里展示同步历史和失败项列表。
- 宽屏可使用平台网格或左侧平台列表 + 右侧平台详情；移动端进入单个平台详情页。

#### AI 模型

AI 模型设置用于低频配置，不承载日常 AI 结果浏览：

- 文本模型、视觉模型、摘要模型、Embedding 模型分组展示。
- 每组显示当前供应商、模型名、配置完整度和最近连通性结果。
- API key 等敏感字段默认隐藏，编辑时使用明确保存/测试操作。
- 连通性测试结果进入通知中心或任务详情，不在设置页堆完整日志。

#### 媒体与存储

媒体与存储设置用于控制归档和代理策略：

- 图片代理、远程媒体归档、WebP 质量、视频大小限制、媒体数量限制等配置。
- 每组说明“影响未来任务还是立即生效”，避免用户误解。
- 媒体失败的具体样本和重试不在设置页处理，应进入通知中心、任务详情或内容详情。

#### 推送配置

推送配置用于低频配置推送能力：

- Bot 凭证、推送目标、权限配置、白名单/黑名单。
- 目标测试可作为明确按钮存在，但测试结果进入通知中心或任务详情。
- 分发规则和分发队列不在设置页编辑，应进入自动化分发域。

#### 外观与系统

外观与系统用于低风险、低频配置：

- 主题模式、密度、动效偏好、许可、版本信息。
- 后端地址、API token、初始化状态和调试信息可以放入系统区。
- 高风险系统操作需要二次确认，不与普通设置项混排。

账号中心最终收敛到“账号与平台”，不再作为独立工具入口重复存在。

## Shell 与深层页面布局逻辑

前端应统一三种页面外壳：

### Root Shell

用于主入口页面：动态、收藏库、自动化。

- 桌面：侧边主导航 + 顶部工具入口 + 内容区。
- 移动：底部导航只保留动态、收藏库、自动化；搜索、通知、设置放顶部。
- 主导航不包含设置、账号、任务结果、Agent。

### Section Shell

用于二级管理类页面：设置、自动化下钻、通知中心下钻、未来订阅源管理等。

- 桌面：左侧二级列表 / 导航，右侧为有明确层级的当前内容区。
- 内容区可根据场景使用圆角 surface、卡片组、沉浸式 Hero、媒体头图或表单布局；统一要求是清楚表达 active content，而不是强制某一种背景或圆角样式。
- 左右比例可拖动或在断点处切换。
- 竖屏：先显示二级列表，点击进入详情全屏，左上角返回。

### Detail Shell

用于深层详情：内容详情、任务详情、规则详情、失败项详情、平台账号详情。

- 整页换页，不常驻主导航或底部栏。
- 左上角保留返回按钮。
- 支持预测性返回手势。
- 返回时恢复来源页面滚动位置和选中状态。

这套 Shell 逻辑用于解决当前“深一级界面仍挂着常驻侧边栏/底部栏”的生硬问题。

## 重试、撤销和中止设计

### 重试

重试不应到处显式铺按钮。分层原则：

- 后端默认重试：网络波动、临时 5xx、媒体下载、短暂模型服务失败等。
- 前端显示后端重试状态：例如“正在重试 2/3”。
- 显式重试只用于用户修复根因后：重新登录、修复推送目标、调整配置、恢复平台能力后。
- 开发调试用重试可以隐藏到高级/调试入口，不作为普通用户主操作。

### 撤销

撤销适合已完成且可逆的本地状态变更：删除收藏、忽略动态、标记稍后、修改标签、移出队列等。

- 主交互使用 Snackbar：`已删除 1 条收藏 [撤销]`。
- 后端应尽量支持 soft delete 或 undo token。
- 已发生的外部副作用（例如已推送消息）默认不可撤销，只能给出后续补救动作。

### 中止

中止适合正在运行的长任务：收藏同步、批量解析、媒体归档、批量 embedding、长 AI 任务。

- 全局入口：通知中心“正在运行”列表。
- 局部入口：相关业务页面当前运行卡片。
- 后端任务需要支持 `cancelable`、`cancel_requested`、`canceled` 等状态。
- 不使用长时效 toast 承担稳定中止入口。

## Material / Gmail 借鉴原则

- Adaptive navigation：桌面 NavigationRail / side panel，移动 bottom navigation，深层页面全屏返回。
- List-detail：动态流、收藏库、通知中心和设置页在大屏下优先使用列表 + 详情结构。
- Snackbar undo：删除、忽略、归档、移出队列等可逆动作使用撤销反馈。
- Predictive back：内容详情、任务详情、设置详情、图片全屏等深层页面必须支持清晰返回路径。
- Performance：列表虚拟化、图片缓存、详情预取、返回时保留滚动位置，避免动画导致整页重建。
- Material 3 expressive：使用清晰层级、圆角 surface、低干扰动效和有目的的 shared transition。

## 实施步骤

1. 文档对齐阶段：更新 `docs/frontend/*` 页面职责文档，标明目标信息架构和旧页面降级方向。
2. 路由与 Shell 设计阶段：设计 Root Shell、Section Shell、Detail Shell 的路由关系、断点、返回逻辑和过渡动画。
3. 通知中心设计阶段：定义通知类型、任务摘要、运行中任务、中止入口和 `/tasks/:runId` 跳转关系。
4. 动态页重定义阶段：将动态页从 dashboard/今日状态改为信息流设计，定义 feed item、digest item、排序筛选和详情预览。
5. 收件箱降级阶段：将 Discovery/Inbox 的候选浏览和收藏/忽略/稍后能力并入动态信息流；旧 `/inbox` 入口降级或重定向。
6. 收藏库增强阶段：完善筛选三态策略、卡片到正文转场、多媒体详情和搜索/RAG 预留入口。
7. 自动化重构阶段：建立自动化总览、收藏同步、分发、解析/后处理三大域和下钻列表。
8. 设置重构阶段：实现 Section Shell 设置页，账号中心并入“账号与平台”。
9. 重试/撤销/中止阶段：对前端动作和后端任务 contract 进行统一梳理，移除无意义显式重试，补通知中心中止能力。
10. 验证与收敛阶段：更新问题文档状态、截图验收、路由回归、桌面/移动断点验收和性能检查。

## 验收标准

- 信息架构：主导航只保留动态、收藏库、自动化；通知中心和设置不作为主导航项。
- 动态页：能够展示订阅/发现/AI 推荐信息流，并用 digest 形式展示收藏同步新增摘要。
- 收件箱：不再作为主导航入口；收藏、忽略、稍后能力能在动态流中完成。
- 收藏库：筛选在移动、中等屏、宽屏下分别使用 bottom sheet、展开面板和可 pin 侧栏；卡片到正文转场不出现重叠残影。
- 自动化：默认页只展示概览和三大域摘要；历史列表、失败列表、规则详情等进入下钻页面或折叠区域。
- 通知中心：能展示运行中、需要处理、最近完成三类通知；运行中可取消任务有明确中止入口。
- 设置：桌面端使用左侧设置列表 + 右侧有明确层级的当前内容区；灰色背景圆角 surface 仅作为设置/表单场景的推荐表达之一。竖屏下收折为列表到详情的全屏导航。
- 深层页面：内容详情、任务详情、规则详情、设置详情等不保留常驻主导航，提供清晰返回与预测性返回路径。
- 重试：普通失败不铺满显式重试按钮；只有修复根因后才展示明确重试动作。
- 撤销：删除、忽略、移出等可逆操作提供 Snackbar undo。
- 验证：`flutter analyze`、`flutter test` 通过；桌面、平板、手机竖屏、手机横屏均完成截图或录屏验收。

## 风险

- 技术风险：当前路由和 `StatefulShellRoute` 可能与深层页面全屏换页目标冲突，需要重构路由层级和返回状态保持。
- 技术风险：动态页吸收收件箱能力后，需要重新定义 discovery/feed API contract 和前端状态模型。
- 技术风险：通知中心需要后端任务状态、取消能力、进度和通知分类支持，可能触及后端任务模型。
- 产品风险：移除独立收件箱和账号中心可能影响已有使用习惯，需要通过过渡入口或 redirect 降低迁移成本。
- 产品风险：自动化页下钻后，部分高频操作可能比现在多一步，需要通过概览卡和快捷入口平衡效率。
- 回滚策略：实施应按阶段提交；Root Shell、动态页、自动化页、设置页分别可独立回滚。旧路由可在短期保留 redirect，但不保留重复 UI 职责。
