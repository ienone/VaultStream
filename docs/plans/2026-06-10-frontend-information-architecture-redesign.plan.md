# 前端信息架构与自适应 UI 重设计规划

## 状态

active

## 文档职责

本文只记录仍然有效的产品结构、设计原则、剩余工作和验收边界。已经执行的路由、页面和代码变更见同名 `process`；当前界面事实见 `docs/frontend/`。这里不保存 Widget 树、组件参数或阶段操作日志。

## 背景

VaultStream 已形成收藏、动态、自动化、设置、任务和 Agent 等页面，但长期迭代造成入口职责重叠、后台管理感过强、信息密度失控和自适应行为不统一。前端需要围绕个人知识流重新组织，而不是继续给既有页面堆叠卡片和操作。

## 目标

- 主导航只保留高频、长期稳定的用户任务。
- 动态、收藏、自动化、设置、任务和 Agent 各自拥有清晰主职责。
- 手机、平板、桌面和横竖屏使用同一信息架构，并以不同布局表达。
- 贯彻 Material 3 Expressive 的层级、形状、颜色和动效原则，但不被默认组件外观限制。
- 减少重复入口、重复结果展示、图标加文字按钮堆叠和不必要弹窗。
- 为预测性返回、共享转场、键盘/鼠标和原生媒体控制保留稳定导航边界。

## 非目标

- 本计划不定义后端新 API、数据库字段或 Agent 工作流。
- 不以一次视觉换肤替代信息架构整改。
- 不恢复已删除的收件箱、账号中心或旧 Review 页面。
- 不为旧路由、旧页面或旧状态容器保留长期兼容层。

## 核心信息架构

### 动态

动态是用户每天进入后浏览信息变化的首页，目标形态是经过去重、排序和解释的信息流。

它负责：

- 展示订阅、发现、同步和 Agent 推荐形成的近期内容流。
- 提供轻量收藏、忽略、稍后处理和进入详情的动作。
- 解释推荐或聚合理由，并允许用户修正。
- 呈现少量真正需要立刻处理的异常。

它不负责长期承载系统仪表盘、完整队列管理、收藏统计或任意任务 JSON。

### 收藏库

收藏库是稳定资产入口，负责浏览、搜索、筛选、批量维护和进入内容详情。语义搜索与传统筛选应在同一搜索体验中切换，不能形成两个割裂页面。

收藏卡片优先表达内容本身：标题、来源、时间、代表媒体和少量状态。系统内部阶段和低频操作不应占据卡片主体。

### 自动化

自动化采用“概览—领域—对象详情”层级：

- 概览只显示收藏同步、分发、解析/后处理三类自动化的健康与待办。
- 领域页承担配置、队列、历史和批量操作。
- 单个规则、目标、运行或失败项进入详情页面或恰当的 adaptive surface。

自动化页不承担账号登录主流程、全部系统设置或跨领域任务详情复制。

### 设置

设置只承载低频、全局且由用户明确控制的配置。账号与平台是设置中的强分区，负责连接、检测、解绑和修复，但不恢复独立账号中心。

设置项必须对应真实后端能力；未实现策略不能作为可点击占位项出现。

### 任务与通知

任务结果页是一次后台运行的统一详情落点。通知中心负责聚合完成、失败、需要确认和高时效事件；它们共享任务摘要，但不重复实现各业务域的完整操作界面。

### Agent

Agent 是受控的自然语言工作区，不进入底部主导航。它负责会话、证据、工具过程和确认；确定性高频操作仍由常规页面提供。

## 导航层级

- Root Shell：动态、收藏库、自动化。
- 工具入口：通知、设置；Agent 通过明确入口或深链接进入。
- Section Shell：设置分区、自动化领域等二级工作区。
- Detail Shell：内容、任务、规则、目标、来源和运行详情。

旧 `/inbox`、`/discovery`、`/accounts`、`/dashboard`、`/review` 已删除，不保留 redirect。后续能力直接落入新的职责页面。

## 自适应原则

### 手机

- 根级入口使用底部导航；深层页面使用全屏前进/返回。
- 主要操作靠近拇指区域，批量和低频动作进入底部操作面。
- 横屏不能简单沿用竖屏加宽版，应避免顶部和底部栏同时挤压内容。

### 平板与桌面

- 根级入口可使用 NavigationRail 或侧栏。
- 有稳定选择关系的页面优先 list-detail；没有稳定主从关系时不要强行双栏。
- 限制正文和表单阅读宽度，把额外空间用于上下文、目录或预览，而不是无限拉伸。

### 返回与状态保持

- Android 预测性返回必须能预览真实目标页面，不被多层透明路由或重复 Hero 阻断。
- 旋转和断点切换后保留当前分区、筛选、选择对象与阅读位置。
- 弹窗、底部面板和详情页的返回层级必须一致，不能依赖视觉上相似但语义不同的关闭按钮。

## Material 3 Expressive 原则

- 先建立颜色、形状、间距、排版和动效 token，再统一组件。
- 形状应体现层级与操作语义；可以使用更柔和的圆角选择控件，不照搬不合适的默认直角样式。
- 图标只用于高辨识度动作；含义不明确时使用清楚的文字，不堆叠“图标 + 标题 + 副标题 + 状态 + 箭头”的重复表达。
- 同一区域只保留一个主要操作，次要操作降级为菜单或上下文动作。
- 动效用于解释层级、选择和连续性，不为每张卡片添加独立装饰动画。
- 颜色不单独承担状态表达，错误、运行中和完成状态同时提供文字或形状线索。

## 页面收敛规则

- 一个用户职责只能有一个主入口；其他位置只做摘要和跳转。
- 任务结果、健康状态和错误详情必须复用统一表达，不在多个页面复制 renderer。
- 页面文档记录用户可见能力、状态和自适应变化，不记录 Widget 组合。
- 复杂编辑优先独立详情页；只需短暂确认或少量字段时才使用 dialog/bottom sheet。
- 删除旧实现时同步删除旧 provider、组件、测试和文档，不保留隐藏 fallback。

## 实施阶段

1. 收敛文档、设计 token 和页面职责，建立多断点基准截图。
2. 重构动态页，使其从统计 Dashboard 转为真实信息流。
3. 收敛收藏卡片、详情模板、搜索和媒体体验。
4. 将自动化三大域拆成稳定的 Section/Detail 层级。
5. 重建账号与平台分区，补齐通知中心和统一任务结果。
6. 完成预测性返回、横屏、平板/桌面和性能验收。

## 验收标准

- 主导航及各页面职责与 `docs/frontend/` 一致，不存在重复主入口。
- 动态首屏以内容流为主，不再由统计卡和后台诊断主导。
- 收藏、自动化、设置、任务和 Agent 的主要任务能在两级以内到达。
- 手机竖屏、手机横屏、平板和桌面均有可复现截图与交互验收。
- 预测性返回、键盘导航、屏幕阅读、触控目标和文本缩放通过检查。
- 页面不再直接堆叠重复 API 写逻辑，关键动作有统一控制层和测试。
- 不再出现无意义图标、重复说明、不可用占位设置和多套任务详情。

## 风险

- 信息架构与视觉重构同时推进可能扩大回归面，应按页面切片验收。
- 当前 API 按旧页面组织，前端收敛可能暴露 contract 缺口；应先记录 issue，不在调用方猜测兼容。
- 自适应和转场依赖真实设备验证，单一桌面模拟器不足以验收。
- Animeko 与 Gmail 只作为组织逻辑参考，不能直接复制其产品职责或平台假设。
