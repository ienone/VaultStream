# 后端模块：多来源自动聚合

## 状态与入口

active。本模块实现默认关闭的周期模型工作流，不替代单条摘要或人工事件管理。

- `services/content_aggregation_service.py` 编排策略、模型、验证与运行记录。
- `schemas/content_aggregation.py` 固定模型输出结构。
- `repositories/content_aggregation_repository.py` 保存生成文章、事件成员及进度。
- `DiscoverySyncTask` 在已有周期循环中检查，不创建第二套 scheduler；即使未配置订阅源，也会检查已保存内容。
- 自动化 → 处理提供 `enable_content_aggregation` 和 `enable_aggregation_push` 两个独立开关，默认均 false。

## 输入、输出与进度

每次最多取 20 条按 `updated_at,id` 排序的新增/更新内容，并补充最多 10 条较早来源作为关联上下文；优先取新材料所属的未被人工修改的自动事件来源，其余名额取最近七天来源，必须已解析、有正文、未删除且不是综合稿；排除忽略、稍后、合并和过期候选。首次处理最近 24 小时，之后读取持久游标。不足两条等待后续来源，不调用模型；每次尝试至少间隔一小时，模型调用最多 90 秒。每条发送标题和正文前 6000 字符，使用现有文本模型工厂与配置。

模型只将同一具体事件的至少两个来源组成组，返回结论、来源 ID、逐字短引句与主题标签；找不到共同事件可以返回空分组。调用通过 LangChain function calling 直接绑定现有 `AggregationOutput`，缺失工具调用或无效字段直接失败，不做 JSON 正则提取、修复或回退。随后继续严格验证字段、数量、来源范围与引句存在性。结构和引句验证不证明结论真实性或逻辑蕴含，因此文章明确标注 AI 生成、未经核实，所有事件成员均为 unverified，综合稿为 report，原文为 source，added_by 为 workflow。

保存前在同一写事务中核对全部输入版本，再新建综合稿及来源，创建事件或向符合版本条件的自动事件追加成员，最后保存 `content_aggregation_cursor`。来源变化、越界引用、无效引句、模型错误或关闭开关后的迟到结果不提交产物和游标。按来源 ID/标题/正文摘要建立生成内容身份，同一材料重放不重复创建事件。空分组成功会推进游标。

游标附带上一成功批次的 `last_judgment`（材料/契约指纹及当时 `new_source_ids`），空分组同样保存。若只是 ai_score 等不影响材料的字段更新，当前材料和候选事件与上次相同，且当前新来源 ID 是上次已判断范围的子集，则复用成功判断，只推进扫描游标，结果记为 `generated=false`、`reused_judgment=true`。这条路径仍在事务中核对所有来源与候选事件版本，不修改来源的 updated_at，避免自触发。

指纹按来源 ID 稳定排序，覆盖标题、提供的正文、完整正文哈希、canonical_url、is_nsfw，以及候选事件 ID/标题/成员/版本、实际模型地址/名称/参数、提示、schema 和输出上限。标题/正文（含截断之后的尾部）、来源定位/分级、候选上下文、事件或模型契约变化均不复用；当前新来源范围超出上次判断范围时也不复用。新来源仍可以和已处理来源作为历史上下文归组，不把“曾处理过”当作全局排除条件。

此优化只保留上一成功批次，不回溯任意历史组合，也不因模型/提示改变立即重扫旧内容；后续有新扫描材料时按新契约重新判断。旧游标没有 last_judgment 时正常调用一次建立记录。失败不保存成功判断，不推进游标；已有每次尝试一小时间隔保持不变。

工作流不会修改已有人工事件、原文、摘要或人工证据结论。通过历史上下文可关联最多 10 个仍活跃的自动事件，已有关联来源不因超过七天而被排除，模型必须引用候选事件的原来源和本批至少一条新来源。仅当事件版本仍等于上次自动生成记录时允许追加；人工修改前后均受版本检查保护，不改写旧综合稿或事件标题。不进行全库回溯、自动合并/拆分或语义质量保证。游标只推进到新增材料末项，历史上下文不改变进度。

## 运行与分发

运行账本为 content_aggregation，保存输入版本/截断字符数、生成内容与事件 ID，并提供综合稿入口。生成事务成功后才执行事件通知和可选分发，生成成功不等于平台发送成功；发送结果以队列和 pushed record 为准。

聚合推送开关不仅控制新结果：自动审批、规则刷新、enqueue、Agent 排期和 worker 发送前均读取它；关闭会暂缓已有队列。开启后新结果仍走全局分发模式、已有匹配规则、审批、目标可用性与去重。未入队的历史结果需要原有人工审核/入队或规则扫描操作，不因开启开关自动全量补推。已入队失败继续使用原有重试/人工操作；生成与入队之间的进程崩溃不自动重跑模型，未入队结果由原有扫描恢复。

## 本地验证边界

此前的隔离 SQLite 验收使用真实 schema、仓库、内容/事件/游标事务与分发队列，模型和发送网络替换在边界。当时覆盖有效生成、重复生成、空分组、引用越界、虚构引句、源版本变化、关闭后的迟到结果、独立推送开关、目标停用和 Agent 处理中排期保护。随后使用真实 deepseek-flash 验收人工构造的三条材料，正确续接指定事件、排除无关材料内的指令且全部引句核对通过（2582 tokens）。该样本没有覆盖全面质量；私有来源聚合与 Telegram/QQ 外部接受尚未验证。

2026-09-26 补查使用真实 ConfigService、服务、仓库、运行账本和隔离 SQLite，模型返回受控，验证空分组后轮流只改两条来源的评分均为零新增模型调用且推进游标；真实材料、上下文、事件、模型/提示/schema 变化重新调用。新来源与旧来源共同进入输入；来源/事件在模型等待或复用提交前变化、模型失败和伪造引句均不推进游标，下一轮仍可重试。未用此控制验收推断真实模型分组质量或生产节省比例。
