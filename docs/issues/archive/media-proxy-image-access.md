# 图片代理和媒体访问修复记录

## 状态

archived

## 现象

旧详情页和卡片曾把多数外链图片默认改写为后端代理，代理任一步失败后只显示无语义的红色失败块。当前链路已改为后端媒体资产与有序来源 contract；普通外链不再由前端默认代理。

## 影响范围

- 收藏卡片封面。
- 内容详情首屏头图。
- 富文本图片和媒体网格。
- 分发缩略图。

## 复现方式

1. 打开包含外链图片的收藏内容详情页。
2. 检查前端是否把图片 URL 改写为 `/api/v1/proxy/image?url=...`。
3. 断开或限制上游图片访问，或使用需要特殊 Referer/Cookie 的图片 URL。
4. 观察详情页是否只显示红色失败块，而没有明确失败原因。
5. 对本地 `local://` 媒体和直接可访问外链分别重复验证。

## 根因分析

前端 `media_utils.mapUrl` 对许多外链强制走 `/proxy/image`，甚至所有其他 `http/https` 外链也会走代理。后端 `/proxy/image` 不只是透明代理，还执行 SSRF 检查、下载、像素校验、WebP 转码和本地缓存。任何步骤失败都会让图片不可见。

真实知乎样本还暴露出两个网络边界问题：代理对单次连接失败过于敏感；Windows 网络栈可能把本机代理的 `198.18.0.0/15` Fake-IP 表示为 IPv4-mapped IPv6，旧逻辑会误判为内网地址。代理传输层现对连接失败执行 2 次受控重试，并等价识别这两种 Fake-IP 表示；其他 SSRF、重定向、体积和像素校验保持不变。

另一个真实运行样本中，同一公网图片域名在常驻后端进程内二次解析为 `127.0.0.1`。SSRF 层必须继续拒绝该结果，不能为了消除裂图而放行回环地址。该场景说明展示层需要持有经过后端判定的多个媒体候选，而不是依赖单个代理 URL。

当前 `cover_url`、`thumbnail_url` 和 `media_urls` 只表达单个字符串；归档元数据虽然保留 `orig_url`、本地存储 key 和缩略图 key，内容展示 contract 却没有把它们组织为候选链。后续应统一为“媒体资源 + 有序来源”模型：本地转码/缩略图优先，远端代理与原始 URL 按安全策略降级，并复用于封面、头像、正文图片及未来的音视频来源选择。

2026-07-28 的运行时排查还确认了卡顿放大链路：冷缓存请求会先把远端响应完整聚合到内存，随后在异步路由所在事件循环中同步执行 Pillow 像素校验和 WebP 转码；同一 URL 没有 singleflight 或并发上限，因此卡片、详情和缩略图同时请求时会重复下载、重复解码。现场日志记录到同一知乎图片在同一秒发生两次独立冷请求；无外部请求的健康检查也出现约 0.47–1.06 秒响应时间。

2026-09-05 静态复核：缓存配额目录遍历已由 `asyncio.to_thread` 执行，不再是“每次在事件循环同步扫描”；但 `_image_to_webp` 的 Pillow 解码/转码仍在 async handler 内同步执行，冷 miss 仍会触发配额扫描。转码、存储或配额维护异常仍共同降级为原始缓存路径，cache hit 固定以 `image/webp` 返回，因此错误分类和 MIME 真实性仍是当时的问题。

当前处置（2026-09-05）：像素校验和 WebP 解码/转码已移出事件循环；缓存查找同样在线程执行。缓存命中按实际扩展名返回 MIME，不再固定伪报 WebP。转码失败只降级当前原图；缓存写入失败与配额维护失败分别记录，并通过 `X-Cache-Persist` 暴露，不能再被记成“转码失败”或触发第二次原图写入。原图只有在 MIME 与扩展名可稳定互推时才缓存。同 URL 冷请求现在由 URL hash 锁合并，等待者会在锁内复查缓存；不同 URL 的下载、像素校验和解码/转码最多并发 4 路。配额在进程首次成功写入及其后每 16 次成功写入检查一次，避免每个冷请求全量扫描，同时把检查间隔内的临时增长限制在 15 个单图上限内。前端旧 URL 映射不再默认代理普通外链，资源级签名和公开代理请求不携带全局 API Token；嵌套引用、全屏图集、卡片和队列预览已持有统一资产候选。过期签名按资产单次刷新，404 本地来源由服务端核验后标记修复状态；签名 blob Range 回归通过，播放器会请求 playback 候选并在运行期切源时恢复进度。Telegram/QQ 分发 payload 也已改为从资产/变体选择本地上传源与允许直连的远端兜底，push service 不再读取旧 archive metadata/cover_url。仓库实验库已贯通到 Telegram 适配器的本地文件上传边界；真实浏览器/原生长媒体、后台播放和真实平台发送尚未验收。

该次检查中数据库和应用配置均未启用 `http_proxy`，当前知乎/小红书图片域名解析到允许的 `198.18.0.0/15` Fake-IP。日志中的 `127.0.0.1` 拒绝属于此前网络状态；它会造成图片失败，但不能单独解释当前持续卡顿，不能通过放宽 SSRF 回环地址限制处理。

## 关闭结论

1. 普通外链保持直连，只有后端明确返回的代理候选使用 `/proxy/image`；前端不再猜测代理策略。
2. 归档任务优先生产本地变体，manifest 按用途返回本地签名、代理和允许直连的有序候选。
3. 代理缓存继续作为可选加速层；像素校验、转码、缓存查找和配额维护均不阻塞事件循环，缓存写入失败不改变已验证响应。
4. 同 URL 冷请求合并，不同 URL 冷处理限制为 4 路；缓存 MIME、转码失败和持久化失败有独立事实字段与回归。
5. 前端按来源和 HTTP 状态区分签名过期、授权失败、本地缺失、远端不可达、格式不支持和未知失败，候选耗尽后显示语义占位与重试。
6. Telegram/NapCat 分发从统一资产/变体选择本地上传或允许直连来源，不再读取旧归档 metadata/`cover_url`。

## 验证方式

- 使用可直接访问外链、需代理外链、本地 `local://`、无效 URL 四类样本测试。
- 前端 widget/unit 测试覆盖 URL 映射。
- 后端 API 测试覆盖代理成功、SSRF 拒绝、上游超时和 Content-Type 拒绝。
- 真实浏览器/原生长媒体与 Telegram/QQ 发送仍需具备相应网络和授权环境后人工验收；这些外部验收限制记录在媒体组件和页面文档中，不作为本代码缺陷继续保持活动。
