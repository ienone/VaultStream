# 后端测试套件价值密度偏低

## 状态

archived

## 现象

- 默认测试套件数量很多，但测试数量和覆盖率明显高估了实际保障能力。
- 部分测试篇幅过长、准备代码重复，或主要验证 mock、内部实现细节和人为构造的分支。
- 相近场景被拆成大量低信息量用例，存在“为了增加测试而测试”的倾向。
- 历史上真实平台、网络探针和常规单元测试边界不清，默认执行曾触发外部请求；2026-09-06 已修复本轮捕获到的伪 Bot 外联路径，仍需持续守住这一边界。

2026-07-16 的当前基线为：`763 passed, 4 skipped, 9 deselected`，覆盖率 64%，耗时约 228 秒，并出现 3 个资源释放警告。该结果能说明套件可运行，但不能直接证明关键用户流程受到同等强度保护。

2026-07-17，最近一次远端 Quality Gates 又出现 `1 failed, 762 passed, 4 skipped, 9 deselected`，而同一失败用例在本地针对性复测通过。测试价值治理还必须与依赖和环境可复现性一起建设，不能只在当前虚拟环境中删减用例。具体环境问题见 `./backend-ci-environment-reproducibility.md`；只有真正开始该切片时，才根据当时事实建立专项计划。

2026-09-06 的最终本机 Python 3.13 基线为：`1020 passed, 4 skipped, 8 deselected`，无覆盖率运行 18.74 秒，带覆盖率运行 26.77 秒、覆盖率 65%。`ResourceWarning` 已在默认 pytest 配置中升级为错误，默认套件通过 `pytest-socket` 禁止非回环网络；真实外联测试必须显式标记 `integration` 与 `enable_socket`。原先在收集阶段读取仓库数据库模型配置的真实 LLM 用例已移到 `backend/manual_tests/`，常规 pytest 不再加载真实模型配置。

此次治理补齐两个模块级 SQLite 引擎释放、分发 Worker 启动状态任务的停止等待，并把发现/收藏 API 的异步执行交给 FastAPI 受管后台任务；测试中的伪 Bot 配置会回收，失败场景改为故障注入。收藏同步测试不再真实等待 12 秒限流；媒体下载测试跳过真实退避但固定重试次数；生产媒体归档对 `UnsafeUrlError` 立即拒绝，不再把确定的 SSRF 拒绝重试三次。发现封面优先级测试隔离与断言无关的归档和后处理。

关键风险、测试分层、网络边界和慢测试规则已进入 `docs/backend/testing.md`。当前最慢 5 项均为队列并发/吞吐、优雅重启和本地 HTTP 控制面测试，保留其真实时序或协议价值。原先可复现的资源泄漏、默认外联和无意义生产等待均已消除；后续发现具体重复或脆弱用例时按对应领域处理，不再用笼统的“测试数量过多”保持本 issue 活动。

## 影响范围

- 后端：`backend/tests/`
- CI：测试反馈时间较长，失败信号容易被大量低价值用例淹没。
- 重构：测试过度绑定实现细节时，会阻碍合理重构，却不能有效发现行为回归。
- 维护：重复 fixture、重复构造数据和冗长断言提高阅读与修改成本。

## 根因分析

- 过去将测试数量和覆盖率当成主要完成指标，缺少按业务风险分配测试成本的规则。
- API contract、领域不变量、后台任务边界和外部适配器行为没有形成清晰的测试分层。
- 单元测试、集成测试、真实平台探针和手工调试脚本曾经混放。
- 缺少对单个测试所防止的真实故障、运行耗时、重复覆盖和脆弱性的持续审查。

## 修复建议

### 第一阶段：建立价值判断

- 先列出捕获、解析、存档、搜索、队列、鉴权和外部副作用等关键用户流程及不变量。
- 将现有测试映射到这些风险；无法说明防止何种真实回归的测试，列为合并或删除候选。
- 记录慢测试、重复测试、脆弱 mock 和只验证实现细节的测试。

### 第二阶段：收敛测试分层

- 少量契约测试保障 API 输入、输出、状态码和错误语义。
- 聚焦单元测试保障复杂纯逻辑与领域不变量，不重复覆盖框架行为。
- 集成测试保障数据库事务、任务编排和适配器边界，并使用明确 marker。
- 真实平台探针继续放在 `backend/manual_tests/`，不得作为常规 CI 通过条件。

### 第三阶段：提高信号质量

- 合并只有输入值不同、风险相同的冗余参数化场景。
- 优先补关键失败路径、权限边界、幂等性、并发和数据一致性测试。
- 修复资源释放警告，并为测试耗时和不稳定性建立基线。
- 覆盖率只作为未测试区域的线索，不作为新增测试的主要目标。

## 验证方式

- 精简后关键流程和历史高风险缺陷仍有明确自动化保护。
- 默认套件耗时显著下降，且不访问真实网络或真实平台。
- 删除或合并测试时，说明其重复关系和替代保障，而不是仅追求文件或用例数减少。
- 对关键模块尝试基于变异测试或故障注入抽查，确认测试确实能拦截错误实现。
