## CP-01 · 已调整：解析队列遗留 RUNNING 超时失败，不自动接续

**修复前复现：** 向隔离库提交一个 `task_type=parse_content` 的 RUNNING Task，`started_at` 为一天前；重建 TaskQueue 后 `dequeue(timeout=1)` 返回 None。原实现只领 PENDING，正常捕获取消与进程硬中断不能混为一谈。

**当前：** [TaskQueue](../../backend/app/core/queue_adapter.py)每行只执行一次，30 分钟超时后结算失败，不重领同一任务；移除世代和执行预算。[解析提交](../../backend/app/tasks/parsing.py)仍检查任务处于 RUNNING，并重新读取人工编辑/删除，将正文、媒体事实和 Task 完成原子写入。用户可以明确重新发起解析。

**验收：** 临时验收确认失败不重复执行、超时不重领且迟到结果不能提交；既有人工修订、删除和后处理失败边界继续通过。

## CP-02 · 已修复：分发 PROCESSING 遗留且不能安全重放

**修复前复现：** 具备可用目标、规则和可读内容的 PROCESSING 项，`locked_at` 为一天前；新 worker 领取集合为空，状态不变。远端发送与本地记录分两步，单纯把它加入自动重试会产生重复外发风险。

**当前：** [分发状态服务](../../backend/app/services/distribution/delivery_state.py)区分准备、发送边界和未知结果；每次唯一 token 与 10 分钟租约隔离迟到 worker。未调用发送服务的准备中断可有界恢复，未知结果隔离且生成持久核对通知。前端从消息或队列逐条记录实际观察；确认送达需消息 ID，确认未发送不自动排期。普通重试、force、Agent 和其他规则项不能绕过未知结果。

**验收：** 丢失/空回执、取消、过期旧 worker、同目标重复规则和批量请求均不造成自动重发；未知目标不阻塞其他目标。发送前重读目标、规则和策略；暂停时只归类遗留状态。沿用显式人工发送可绕过自动暂停的既有语义，不绕过目标、审批和聚合授权。消息 → 核对两个分支已实际操作，过时观察返回 409。

**2026-09-19 审查修复：** 确认未发送会同事务停止当前同内容、平台、目标的其他已排期或待自动重试项，须另行排期；其他未知、发送中和已送达记录保持。领取前及条件领取时排除停用规则和目标，避免它们反复占据单项领取名额，重新启用后继续原排期。六个失败场景先复现再修复，新增结果与身份保护回归；完整后端 **194 passed**，OpenAPI **150 个端点 / 58 个动作契约**通过。验收使用隔离 SQLite 与模拟发送，无真实外发。

不承诺平台 exactly-once；本地回执记录不能代替用户在目标会话中的实际核对，取消网络请求也不等于撤回远端消息。

## CP-03 · 已修复：候选 TTL 删除综合事件的原始成员

**修复前复现：** 两条已到期 VISIBLE 内容作为事件 SOURCE，生成稿作为 REPORT；运行真实 hard_delete 后只剩 REPORT，原文对象及内部证据关系被级联删除。复制引句和外部 URL 不能替代原始证据。

**当前：** [候选清理](../../backend/app/tasks/discovery_cleanup.py)在 SQLite writer lock 内统一检查“未采纳且无依赖”。事件任意角色成员、用户分享/收藏的 ContentSource、发送队列/记录与父子内容关系阻止独立 TTL 清理；不把所有候选永久保留，也不把保护偷偷转换成用户采纳。

**验收：** hard_delete、archive、expire_only 均保持受保护内容的状态、正文、FTS/embedding 和成员关系；无依赖过期候选仍被正确处理；边界 `expire_at == now` 不提前清理，并发加入事件与清理串行。
