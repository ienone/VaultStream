# VaultStream 文档入口

## 文档状态

active

本目录用于区分当前实现、未解决问题、未来计划和背景知识。文档帮助建立上下文，但当前代码、实际数据和可重复验证结果始终是最终事实来源。

## 事实优先级

1. 当前代码、数据库和可重复验证结果。
2. `frontend/`、`backend/` 中的当前实现文档。
3. `issues/` 中的未解决问题。
4. `plans/` 中的愿景、路线和实施计划。
5. `knowledges/` 中的平台资料、评估样本和外部研究。

如果文档与代码不一致，必须指出并修正文档，不能为过期文档添加兼容逻辑。

## 目录边界

- `frontend/`：前端当前实现、页面职责、导航与共享组件边界。
- `backend/`：后端当前实现、模块职责、API 和数据库事实。
- `issues/`：跨会话仍未解决、需要后续追踪的问题。
- `plans/`：系统构想、开发路线和成规模实施计划。
- `knowledges/`：平台行为、外部参考、评估集和历史材料。
- `*/archive/`：仍有长期决策价值的历史记录；普通过时文件可以删除并依赖 Git 历史。

## 阅读入口

### 前端任务

1. `frontend/README.md`
2. 涉及路由或入口时读取 `frontend/navigation.md`
3. 修改页面时读取对应 `frontend/pages/*.md`
4. 修改共享交互时读取对应 `frontend/components/*.md`

### 后端任务

1. `backend/README.md`
2. 修改业务模块时读取对应 `backend/modules/*.md`
3. 涉及 API 时读取 `backend/api.md` 和对应领域分册
4. 涉及数据库时读取 `backend/database.md` 和对应领域分册

### 计划与问题

1. 理想产品形态：`plans/2026-07-15-vaultstream-system-concept.plan.md`
2. 开发顺序与阶段出口：`plans/2026-07-17-vaultstream-development-roadmap.plan.md`
3. 当前问题：`issues/README.md` 和相关 issue
4. 进入具体领域后再读取对应专项 plan/process

## 文档类型与状态

### 当前实现文档

适用于 `frontend/` 和 `backend/`。

- `active`：当前有效。
- `archived`：只保留历史参考。

当前实现文档只描述代码现在做什么。未来整改只链接 issue 或 plan，不在这里重复方案。

### 系统构想与路线

- `draft`：仍在讨论。
- `active`：当前采用的产品方向或开发路线。
- `archived`：已被新构想或路线替代。

系统构想与路线不需要 process；其修订历史由 Git 和文档内的关键决策说明承担。

### 实施 Plan

- `draft`：尚未确认。
- `active`：已确认，可以进入实施队列，但不表示正在执行。
- `complete`：目标与验收已经完成。
- `archived`：完成或被替代后保留的长期记录。

只有多轮、跨会话或高风险计划在实际启动后才需要同名 process。小型修复使用 issue、提交或 PR 即可，不单独创建 plan。

### Process

- `in_progress`：计划正在执行。
- `blocked`：存在明确阻塞。
- `complete`：执行与验证完成。

Process 只记录关键决策、已完成阶段、偏离原因、验证结论、阻塞和下一步。不要复制完整命令输出、逐文件变更清单或 Git 历史。

### Issue

- `active`：已确认且未处理。
- `in_progress`：正在修复。
- `blocked`：暂时无法继续。
- `archived`：已解决、失效或被其他问题吸收。

架构债务不必伪造复现步骤或根因；可以用代码证据说明现象，并把未知部分标为“待验证”。立即修复且不会跨会话遗留的问题不强制建立 issue。

### Knowledge

- `active`：当前可参考。
- `archived`：可能过期，仅供历史追溯。

Knowledge 解释背景，不直接承载待办或实施步骤。

## 必须遵守的规则

- 当前事实与未来计划分开。
- 跨会话未解决的问题必须能在 issue 中找到。
- 成规模计划必须说明目标、非目标、范围、阶段出口和风险。
- 正在执行的长期计划必须有可接手的进度与验证记录。
- 不确定结论标为“待验证”。
- 删除旧实现时同步删除或更新对应现状文档。
- 文档不得包含失效相对链接、控制字符或已删除能力的错误现状描述。
- 未执行的验证必须明确写出，不能用局部通过代替完整通过。

## 建议而非强制

- 页面和模块文档可按任务调整章节，不要求机械填满统一模板。
- 单人项目不强制填写 owner；出现多人协作后再按领域指定维护者。
- 完成的临时计划和 issue 不必全部归档；没有长期决策价值时可以删除。
- 索引只承担导航，不复制各文件的完整摘要、实施步骤和状态历史。

## 最小文档结构

### 当前页面或模块

- 文档状态
- 当前代码位置
- 当前职责与明确不承担的职责
- 关键输入、输出和副作用
- 关联 API、数据或页面
- 当前问题链接

### Issue

- 状态
- 现象或代码证据
- 影响范围
- 期望结果或修复方向
- 验证方式

复现步骤、根因和详细方案按问题性质选填。

### Plan

- 状态
- 背景、目标与非目标
- 关联问题和当前事实
- 变更范围与阶段
- 可检查的验收标准
- 风险和回滚边界

### Process

- 状态与对应 plan
- 已完成阶段和关键决策
- 偏离、阻塞与剩余工作
- 验证结论和未验证项

## 归档与删除

- 保留影响长期架构、数据兼容、产品职责或安全边界的历史决策。
- 普通执行日志、一次性排查记录和已被新文档完整吸收的内容可以删除。
- 归档文件必须标明已归档，不再作为当前实现或当前计划使用。
- Plan 使用 process 时，完成后一起归档或一起删除，避免孤立文件。

## 最低维护检查

- 文档不存在控制字符和损坏编码。
- 相对链接指向存在的文件。
- `draft` plan 不配 `in_progress` process。
- 每个 process 都能找到对应 plan。
- 当前实现文档的“当前问题”只链接 issue，不复制整改方案。
- 总路线是唯一开发顺序来源，专项计划不得另建冲突的全局顺序。
