# VaultStream 当前产品体验与安全审计

> 日期：2026-06-05  
> 范围：用户视角功能可用性、前后端控制边界、测试可信度、`.codex-security-scans` 安全扫描报告汇总。  
> 主要来源：当前代码路径、最近本地测试结果、`.codex-security-scans/VaultStream/1a616d81_20260530T145418_ws/report.md`。

## 结论

VaultStream 已经具备个人内容收集、解析、检索、发现、审核、分发和 Agent 辅助操作的完整 MVP 形态。它不再只是原型：后端有 FastAPI、SQLite、后台任务、平台适配器、分发规则、SSE、语义搜索和 Agent 工具；前端主导航已收敛为动态、收藏库、收件箱、自动化四个任务入口，并保留设置、连接引导、账号中心和 Agent 辅助页面。

但如果目标是“可长期无人值守的自动收藏与分发系统”，当前还不够成熟。核心问题不是功能数量不足，而是关键自动化链路仍缺少足够完整的运行结果、失败原因、重试入口和精细控制。动态页已开始把后台异常、解析积压、待分发和收件箱候选聚合到首屏，但用户仍需要更完整的事件流、结果页和失败恢复入口，才能稳定判断一次操作是否真正完成、失败在哪里、是否影响了预期范围之外的内容或分发目标。

## 当前可用能力

### 内容收集与解析

- 前端添加 URL 后调用 `/shares`，后端创建内容并放入解析队列。
- 解析任务成功后会更新内容状态，并触发摘要、向量索引、巡逻评分、分发等后处理。
- 收藏库监听 `content_created`、`content_updated`、`content_deleted` 等 SSE 事件，可以随着后台状态变化刷新。

### 发现与入库

- 后端存在发现源同步任务、清理任务和巡逻评分逻辑。
- 当前实际可用的发现源主要是 RSS 和 Telegram Channel。
- 发现内容可以进入评分、可见/忽略和后续入库流程。

### 审核与分发

- 后端有分发规则、目标、队列、审核、立即推送、重试、取消等能力。
- 前端提供审核队列和规则配置入口。
- 分发系统已从“概念功能”进入真实业务模块阶段。

### 账号连接与自动化

- 前端有连接引导、平台登录状态检查、扫码连接和登出入口。
- 后端有浏览器登录服务、Cookie 持久化、保活任务和收藏同步任务。
- 收藏同步已有平台级实现，但尚未达到用户可放心依赖的完整体验。

## 主要体验痛点

### 1. 后台任务缺少统一可观测性

很多操作只返回“已触发”或关闭弹窗，例如添加内容、发现源同步、收藏同步、手动分发。真正的解析、同步、摘要、索引、评分、推送失败都可能发生在后台。

用户目前难以回答：

- 刚才同步了多少条？
- 哪些失败了？
- 是登录失效、平台 403、LLM 配置错误、网络失败，还是解析器问题？
- 失败后是否会自动重试？
- 我应该在哪里手动修复？

当前已有等价的最近运行记录结构，已覆盖解析主队列、收藏同步、发现源同步、巡逻评分、语义索引重建、单条自动 Embedding、内容重新解析、手动摘要生成、单条分发队列立即推送、content-level/批量分发立即排期，以及分发 worker 自动轮询任务：手动触发会返回 `run_id`，后台诊断响应可列出最近运行状态。动态页已在顶部新增“待处理动态”摘要，聚合后台异常、解析积压、待分发和收件箱候选；动态页还新增运行时间线，可查看单次 run 详情抽屉，并从最近后台 run 进入收藏同步、分发历史、收件箱或收藏库，其中收藏同步 run 会携带 Run ID 跳转并自动打开对应结果摘要，内容详情后处理动作也可携带 Run ID 跳到动态页并自动打开对应运行详情。后台诊断卡仍展示最近运行，并可查看单次 run 的状态、错误、元数据和结果。

### 2. 收藏夹自动同步还只是雏形

当前代码中已经有收藏同步任务和设置入口，不能说完全未实现。但从用户视角，它更接近“平台级收藏导入器”，还不是完整的“自动同步登录账号收藏夹”功能。

当前已补齐的部分：

- 手动触发会返回 `run_id`。
- 状态接口包含最近同步运行记录。
- 自动化页已新增收藏同步标签，可查看平台同步状态、最近同步任务、单次任务状态/错误和结构化 result 摘要，并可预览、手动触发和对失败 run 重试。
- 手动触发前已有首版导入预览：后端 `POST /api/v1/favorites-sync/preview` 会只读拉取本轮候选，估算新增/重复/跳过数量，并返回少量候选样本；前端会在单平台或全平台手动同步前展示预览样本并要求确认，不写入内容且不推进 cursor。
- 自动化页已展示当前真实同步策略：已启用平台范围、按平台 cursor 增量拉取、单轮上限/间隔、重复内容策略、远端取消收藏处理策略、run 级失败重试；同步间隔、单轮上限和重复内容策略可在自动化页直接调整，并保留高级参数入口。

仍然存在的缺口：

- 已有从动态页收藏同步 run 到自动化页对应结果摘要的跨页面跳转；预览阶段能看到候选样本，导入阶段单条失败会显示更完整的失败诊断列表、失败总数和截断状态，并可按单条失败候选重试。但还没有完整独立同步结果页和完整失败列表页。
- 没有收藏夹/分组级选择。
- 重复内容策略已产品化为 `merge/skip` 可选配置；取消收藏、删除和冲突策略仍只有当前行为说明，尚未成为用户可选择的策略配置。
- 同步失败时，错误不容易和账号登录状态、平台限制、解析失败关联起来。

建议把收藏同步继续升级为独立产品能力，而不是设置页里的一个后台开关：保留当前平台账号健康、运行记录、导入预览、失败样本展示、失败 run 重试、单条/批量失败项重试和重复内容策略配置能力，继续补齐同步范围、完整失败列表和取消收藏/删除策略。

### 3. 平台账号健康状态分散

登录连接、Cookie、收藏同步、发现同步、解析失败、动态页诊断分布在多个位置。用户遇到“为什么同步不到收藏”时，需要跨页面排查。

当前已补齐的部分：

- 后端提供 `/api/v1/platform-health`，聚合平台 Cookie 配置、浏览器登录检测、收藏同步启用/认证和最近同步 run。
- 连接与账号页已经显示首批平台健康摘要，用户能在一个位置看到登录状态与收藏同步状态。
- 前端新增 `/accounts` 独立账号中心页面，不增加底边栏项；页面聚合平台健康、登录检测、扫码/重新连接、收藏同步预览和最近收藏同步任务。
- 自动化页新增“健康矩阵”标签，聚合平台账号、发现源和推送目标状态，并提供登录检测、平台解析测试、发现源同步、推送目标连接测试、推送目标真实发送测试和推送目标刷新等首批主动操作，帮助用户从自动化工作区看到并处理同步、抓取和推送链路的异常项。

当前补齐：

- 健康矩阵总览提供“查看动态”入口，发现源和推送目标分区提供 Tab 级设置入口，平台账号分区仍可进入账号中心；平台账号行可从最近收藏同步 run 跳转到自动化页对应结果摘要，也可填写 URL 触发一次真实平台解析测试；平台解析测试、发现源同步、推送目标连接测试、推送目标真实发送测试和推送目标刷新均可携带 Run ID 跳到动态页日志；自动化页本身也支持通过 `?tab=` 直达分发队列、收藏同步、健康矩阵或推送历史，用户不需要完全靠记忆跨页面排查。

仍然存在的缺口：

- 健康矩阵目前复用现有状态字段和已有触发接口，平台账号最近收藏同步结果已有聚焦入口，平台解析测试、发现源质量检查、发现源同步、推送目标连接测试、推送目标真实发送测试和推送目标刷新也已有日志跳转；但更多行级后台任务日志跳转和按异常项聚焦的独立结果页仍未补齐。
- 平台能力测试入口仍是首版；解析测试、发现源质量检查和推送目标真实发送测试已有首版真实调用，但尚未形成覆盖失败历史、目标类型差异和多平台边界的完整测试矩阵。

建议建立统一的“账号与平台健康中心”：

- 平台：知乎、小红书、微博、Bilibili、Twitter 等。
- 状态：已登录、Cookie 即将过期、已失效、需扫码、无法验证。
- 最近任务：最近解析、最近收藏同步、最近失败原因。
- 操作：重新登录、刷新 Cookie、测试解析、测试收藏同步。

### 4. LLM 配置过于碎片化

当前系统涉及文本 LLM、视觉 LLM、摘要 LLM、Embedding 和 Agent 模型。工程上可以拆分，但用户很难知道哪个配置影响哪个功能。

建议前端首先展示能力状态，而不是模型字段：

- 内容理解：可用/不可用。
- 摘要生成：可用/不可用。
- 语义搜索：可用/不可用。
- Agent：可用/不可用。

高级配置仍可保留具体 provider、base url、model、api key、dimension 等字段。

当前补齐：

- 后端新增 `GET /api/v1/ai/capabilities`，按配置与语义索引状态聚合内容理解、摘要生成、语义搜索和 Agent 的用户可见能力状态。
- AI 能力页已新增真实连通性测试入口，可对 text LLM、vision LLM、摘要模型和 Embedding 做一次实际调用并记录 `ai_connectivity_test`。
- 前端“大模型引擎”区域先展示能力摘要，再保留文本模型、视觉模型和 Embedding 的高级配置。
- 单条内容的 `processing-status` 已把摘要、语义索引、巡逻评分、分发阶段的配置缺失、失败状态和下一步建议作为 `issues/actions` 返回，详情页会直接展示这些提示。

仍然存在的缺口：

- 解析、平台抓取、Agent 运行和更深层 LLM 调用失败仍未统一接入错误分类；目前只覆盖内容详情后处理状态这一条用户可见链路。

### 5. 错误提示不够产品化

部分前端错误直接显示底层异常字符串。用户更需要可行动的错误分类：

- 平台登录失效。
- 平台安全校验或 403。
- 链接无法解析。
- 后端任务失败。
- LLM/Embedding 配置缺失。
- 推送目标不可用。
- 网络连接失败。

## 前后端控制边界问题

### 1. 分发队列存在操作粒度风险

前端审核队列主体已经改为使用 `queue_item_id` 级接口：移动状态、重排、立即推送、更新计划时间和批量排期均调用 `/distribution-queue/items/...` 或 `/distribution-queue/items/batch-*`。后端也保留了这些 item-level 接口，并有回归测试覆盖 item-scoped status/schedule/reorder/batch 行为。

仍需注意的边界是：后端仍保留 `/distribution-queue/content/...` 这类 content-level 兼容/批量接口。它们适合明确的“对该内容所有目标生效”操作，不应被普通队列单项按钮默认使用。失败推送记录的重推入口虽然仍走 content path，但前端会带 `target_id`，后端只重排该目标并只删除该目标的去重记录；`backend/tests/test_api/test_distribution_queue_extra.py` 已覆盖该边界。

后续要求：

- 继续保持前端默认使用 `queue_item_id` 级接口。
- content-level 接口只用于明确的批量操作或带 `target_id` 的目标级重推。
- UI 在批量操作前显示影响范围，例如“将影响 3 个目标中的 3 条队列项”。

### 2. 发现源支持边界需要持续保持清晰

后端枚举仍保留 RSS、HackerNews、Reddit、GitHub、Telegram Channel，用于表达路线图和历史数据兼容；当前实际可创建、可列出、可手动同步的普通用户来源已收敛为 RSS 和 Telegram Channel。未实现来源在创建或显式查询时应返回结构化错误 `source_kind_not_supported`，后台定时同步也只扫描已支持来源，避免“创建成功但同步无结果”的静默失败。

后续要求：

- 保持前端普通配置入口只暴露 RSS 和 Telegram Channel。
- 新增 HackerNews、Reddit、GitHub 等来源时，必须同时补齐后端 scraper、API 测试和前端表单元数据。
- 不要只扩展枚举或 UI 下拉项，否则会重新引入“看似支持、实际不可用”的体验问题。

### 3. 新增分发目标不回填历史内容

分发规则服务原先默认不会为新增目标生成历史队列项。这可以避免突然产生大量历史任务，但用户可能期望“我新加目标后，旧内容也能补发”。

当前补齐：

- 后端 `POST /api/v1/distribution-rules/{rule_id}/targets` 支持 `backfill_mode`：`new_only`、`recent_days`、`all_history`。
- `recent_days` 支持 `backfill_recent_days`，后端只为解析成功且已审批/自动审批、匹配规则、目标可用的内容补建队列项。
- 前端创建或编辑分发规则时新增“历史内容处理”选择，默认仅新内容；选择回填时 toast 会反馈补建队列数量。
- 后端新增 `POST /api/v1/distribution-rules/{rule_id}/targets/backfill-preview`，前端会在大量历史回填前先预估候选数量并要求二次确认。

### 4. 后处理失败未充分反馈给前端

解析成功后还会触发摘要、Embedding、巡逻评分、分发等后处理。即使主解析成功，后处理仍可能失败。当前这些失败更偏后台诊断信息，不一定进入用户当前操作反馈。

当前补齐：

- 后端新增 `GET /api/v1/contents/{content_id}/processing-status`，聚合单条内容的摘要、语义索引和分发状态。
- 前端内容详情共享信息卡新增“处理状态”面板，横竖屏详情布局和底部详情 sheet 均可展示。
- 状态接口已返回语义索引失败分块和分发失败队列项的最近错误摘要；前端处理状态面板已提供失败详情、摘要生成、单条语义索引重建和分发重试/重新匹配入口。
- 巡逻评分已并入处理状态：接口返回 AI 评分、原因、标签和 discovery state，前端面板展示“巡逻评分”阶段。
- 后端新增 `POST /api/v1/contents/{content_id}/patrol-score`，前端处理状态面板可对待评分/未评分的发现流内容手动触发巡逻评分，并把结果写入 `discovery_patrol` 运行记录。
- 后端新增 `POST /api/v1/search/semantic/embeddings/{embedding_id}/retry`，前端处理状态面板可对语义索引失败分块逐项重试，并记录 `semantic_reindex` 运行日志。
- 摘要生成、语义索引重建和巡逻评分手动触发等返回 `run_id` 的后处理动作成功后，前端 toast 会提供“查看日志”，跳到动态页并自动打开对应 run 详情。
- 摘要、语义索引、巡逻评分和分发阶段已返回 `issues/actions`：例如缺少 `summary_api_key`、缺少 `embedding_api_key`、缺少巡逻评分 LLM key、分发队列失败，并在前端展示“问题/建议”。
- AI 能力状态已提供真实连通性测试：`POST /api/v1/ai/connectivity-test` 会真实调用对应模型/Embedding，并把最近测试成功或失败展示在能力卡中。

仍然存在的缺口：

- 健康矩阵已有平台解析测试、发现源同步和推送目标连接测试的日志入口，但其他区域仍缺更细的行级日志聚焦；平台抓取、Agent 工具调用等链路仍未形成统一错误分类。

## 测试可信度

最近验证结果：

| 范围 | 命令 | 结果 | 结论 |
| --- | --- | --- | --- |
| 后端非 integration | `.venv\Scripts\python.exe -m pytest backend/tests -q -m "not integration" --no-cov` | 734 passed, 4 skipped, 16 deselected | 本地核心逻辑较稳 |
| 后端 integration | `.venv\Scripts\python.exe -m pytest backend/tests -q -m integration --no-cov` | 5 failed, 8 passed, 1 skipped, 2 xfailed | 真实平台/真实外部服务链路不稳 |
| 前端静态检查 | `flutter analyze` | No issues found | Dart/Flutter 静态检查通过 |
| 前端测试 | `flutter test` | 36 tests passed | 基础 widget/unit 测试通过，但覆盖仍有限 |

integration 失败主要集中在真实知乎/小红书内容解析和真实 LLM 调用路径，存在 403、安全校验、连接失败或 cwd 依赖导致 skip 的问题。这说明当前离线单元测试可信，但真实平台功能还不能只靠现有测试证明稳定。

当前补齐：

- 新增 `scripts/product_smoke_check.py`，用于检查运行中后端的健康、初始化、账号健康、AI 能力、收藏同步、后台任务、语义索引、发现源和分发队列控制面。
- 新增 `docs/validation/product-acceptance.md`，区分自动冒烟检查、真实平台人工端到端验收和测试结论口径。

仍需按功能人工验收：

1. 添加普通 URL，确认收藏库出现、解析状态成功、摘要/封面/标签生成。
2. 添加知乎/小红书 URL，确认登录态有效时能解析，失效时错误可理解。
3. 配置 RSS 发现源，手动同步，确认发现列表出现新条目。
4. 配置一个分发目标和规则，确认审核后只影响预期目标。

## 安全扫描汇总

安全扫描报告位于 `.codex-security-scans/VaultStream/1a616d81_20260530T145418_ws/report.md`。扫描方式是 repository-wide Deep Security Scan，包含深度发现、集中验证和攻击路径分析。报告明确说明未运行生产部署、外部网络探测或完整后端端到端服务。

原始扫描结果：

| 指标 | 结果 |
| --- | --- |

| 严重性 | medium=5, low=1 |
| 置信度 | high=3, medium=3 |
| 验证方式 | 静态追踪和有限本地路径模拟 |

当前复核结论：

- `backend/app/routers/media.py` 的本地媒体路径已经使用 `Path.resolve()` + `relative_to()` 校验真实祖先关系，并拒绝 absolute/rooted key；`backend/tests/test_api/test_media.py` 已覆盖 sibling-prefix 路径和正常存储根内路径。因此原扫描中的“公开媒体路由字符串前缀路径检查”不再作为待修项保留。
- `backend/app/bot/permissions.py` 的 Telegram bot 权限已经在白名单为空时 fail closed，管理员仍可使用普通命令，黑名单优先级最高；`backend/tests/test_bot/test_permissions.py` 已覆盖这些边界。因此原扫描中的“Telegram bot 白名单默认允许所有用户”不再作为待修项保留。
- `backend/app/core/safe_fetch.py` 已建立服务端 URL 获取的基础 SSRF 防护；归档图片/视频下载、封面主色远程取图、通用解析 direct HTTP、Playwright 抓取和图片代理均已接入。它会校验 scheme、DNS/IP、redirect 最终目标、响应大小和 content-type；图片代理还通过 `SafeAsyncNetworkBackend` 在 TCP 连接层连接到已校验 IP，并保留原始 Host/SNI。`backend/tests/test_core/test_safe_fetch.py`、`backend/tests/test_media_processor_deep.py`、`backend/tests/test_media_color.py`、`backend/tests/test_adapters/test_tiered_fetcher_security.py`、`backend/tests/test_api/test_media_proxy_security.py` 已覆盖私网地址、私网重定向、类型/大小限制、通用解析阻断和连接 IP 绑定。因此原扫描中的“归档媒体处理缺少 SSRF 控制”“公开图片代理只做连接前 DNS 校验”和“通用分享解析可触发内部 URL 获取”不再作为待修项保留。
- `backend/app/routers/media.py` 的本地媒体 API 已要求 `X-API-Token`/Bearer token，`backend/app/main.py` 已移除 unauthenticated `/media` StaticFiles 挂载；前端 `frontend/lib/core/utils/media_utils.dart` 会把历史 `/media/...` 和裸 blob key 映射到 `/api/v1/media/...`，继续使用同源图片 header 携带 API token；`backend/tests/test_api/test_media.py` 与 `frontend/test/unit/media_utils_test.dart` 已覆盖。因此原扫描中的“本地归档媒体可无鉴权访问”不再作为待修项保留。

当前安全扫描发现已无仍需按原描述整改的未修项。后续安全工作应转入回归监控、依赖审计、生产部署配置校验和新增入口的同类策略复用。
