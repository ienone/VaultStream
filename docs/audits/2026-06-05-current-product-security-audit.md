# VaultStream 当前产品体验与安全审计

> 日期：2026-06-05  
> 范围：用户视角功能可用性、前后端控制边界、测试可信度、`.codex-security-scans` 安全扫描报告汇总。  
> 主要来源：当前代码路径、最近本地测试结果、`.codex-security-scans/VaultStream/1a616d81_20260530T145418_ws/report.md`。

## 结论

VaultStream 已经具备个人内容收集、解析、检索、发现、审核、分发和 Agent 辅助操作的完整 MVP 形态。它不再只是原型：后端有 FastAPI、SQLite、后台任务、平台适配器、分发规则、SSE、语义搜索和 Agent 工具；前端有仪表盘、收藏库、发现、审核/分发、设置、连接引导和 Agent 页面。

但如果目标是“可长期无人值守的自动收藏与分发系统”，当前还不够成熟。核心问题不是功能数量不足，而是关键自动化链路缺少用户可见的运行结果、失败原因、重试入口和精细控制。用户可以触发很多后台任务，但很难确认这些任务是否真正完成、失败在哪里、是否影响了预期范围之外的内容或分发目标。

## 当前可用能力

### 内容收集与解析

- 前端添加 URL 后调用 `/shares`，后端创建内容并放入解析队列。
- 解析任务成功后会更新内容状态，并触发摘要、向量索引、巡逻评分、分发等后处理。
- 收藏库监听 `content_created`、`content_updated`、`content_deleted` 等 SSE 事件，可以随着后台状态变化刷新。

### 发现与入库

- 后端存在发现源同步任务、清理任务和巡逻评分逻辑。
- 当前实际可用的发现源主要是 RSS 和 Telegram Channel。
- 发现内容可以进入评分、可见/忽略和后续入库流程。

### 审核与分发

- 后端有分发规则、目标、队列、审核、立即推送、重试、取消等能力。
- 前端提供审核队列和规则配置入口。
- 分发系统已从“概念功能”进入真实业务模块阶段。

### 账号连接与自动化

- 前端有连接引导、平台登录状态检查、扫码连接和登出入口。
- 后端有浏览器登录服务、Cookie 持久化、保活任务和收藏同步任务。
- 收藏同步已有平台级实现，但尚未达到用户可放心依赖的完整体验。

## 主要体验痛点

### 1. 后台任务缺少统一可观测性

很多操作只返回“已触发”或关闭弹窗，例如添加内容、发现源同步、收藏同步、手动分发。真正的解析、同步、摘要、索引、评分、推送失败都可能发生在后台。

用户目前难以回答：

- 刚才同步了多少条？
- 哪些失败了？
- 是登录失效、平台 403、LLM 配置错误、网络失败，还是解析器问题？
- 失败后是否会自动重试？
- 我应该在哪里手动修复？

建议新增统一的任务运行模型：`task_runs` 或等价结构，记录任务类型、触发来源、目标平台/源/内容、开始时间、结束时间、状态、成功数量、失败数量、错误摘要和重试入口。前端所有异步操作应拿到 run id，并能跳转到任务详情。

### 2. 收藏夹自动同步还只是雏形

当前代码中已经有收藏同步任务和设置入口，不能说完全未实现。但从用户视角，它更接近“平台级收藏导入器”，还不是完整的“自动同步登录账号收藏夹”功能。

主要缺口：

- 没有每次同步的详细结果页。
- 没有收藏夹/分组级选择。
- 没有导入预览。
- 没有明确的重复、取消收藏、删除和冲突策略。
- 手动触发返回 202 后，前端没有 job id 或最终结果。
- 同步失败时，错误不容易和账号登录状态、平台限制、解析失败关联起来。

建议把收藏同步升级为独立产品能力，而不是设置页里的一个后台开关：提供平台账号健康、同步范围、最近运行、失败列表、重复处理策略和手动重试。

### 3. 平台账号健康状态分散

登录连接、Cookie、收藏同步、发现同步、解析失败、Dashboard 诊断分布在多个位置。用户遇到“为什么同步不到收藏”时，需要跨页面排查。

建议建立统一的“账号与平台健康中心”：

- 平台：知乎、小红书、微博、Bilibili、Twitter 等。
- 状态：已登录、Cookie 即将过期、已失效、需扫码、无法验证。
- 最近任务：最近解析、最近收藏同步、最近失败原因。
- 操作：重新登录、刷新 Cookie、测试解析、测试收藏同步。

### 4. LLM 配置过于碎片化

当前系统涉及文本 LLM、视觉 LLM、摘要 LLM、Embedding 和 Agent 模型。工程上可以拆分，但用户很难知道哪个配置影响哪个功能。

建议前端首先展示能力状态，而不是模型字段：

- 内容理解：可用/不可用。
- 摘要生成：可用/不可用。
- 语义搜索：可用/不可用。
- Agent：可用/不可用。

高级配置仍可保留具体 provider、base url、model、api key、dimension 等字段。

### 5. 错误提示不够产品化

部分前端错误直接显示底层异常字符串。用户更需要可行动的错误分类：

- 平台登录失效。
- 平台安全校验或 403。
- 链接无法解析。
- 后端任务失败。
- LLM/Embedding 配置缺失。
- 推送目标不可用。
- 网络连接失败。

## 前后端控制边界问题

### 1. 分发队列存在操作粒度风险

前端审核队列中有多处按 `contentId` 调用后端接口，例如移动状态、重排、立即推送和更新计划时间。后端这些 content-level 接口会查找同一内容的多个队列项并批量操作。

风险是：用户在某个规则或目标视图里操作一条内容时，可能影响该内容在其他分发目标上的队列项。用户预期通常是“只改当前这一条队列项”，而不是“改这个内容的所有队列项”。

建议：

- 前端默认使用 `queue_item_id` 级接口。
- content-level 接口只用于明确的批量操作。
- UI 在批量操作前显示影响范围，例如“将影响 3 个目标中的 3 条队列项”。

### 2. 发现源支持边界需要持续保持清晰

后端枚举仍保留 RSS、HackerNews、Reddit、GitHub、Telegram Channel，用于表达路线图和历史数据兼容；当前实际可创建、可列出、可手动同步的普通用户来源已收敛为 RSS 和 Telegram Channel。未实现来源在创建或显式查询时应返回结构化错误 `source_kind_not_supported`，后台定时同步也只扫描已支持来源，避免“创建成功但同步无结果”的静默失败。

后续要求：

- 保持前端普通配置入口只暴露 RSS 和 Telegram Channel。
- 新增 HackerNews、Reddit、GitHub 等来源时，必须同时补齐后端 scraper、API 测试和前端表单元数据。
- 不要只扩展枚举或 UI 下拉项，否则会重新引入“看似支持、实际不可用”的体验问题。

### 3. 新增分发目标不回填历史内容

分发规则服务中已有设计说明：新增目标不会为历史内容生成队列项。这可以避免突然产生大量历史任务，但用户可能期望“我新加目标后，旧内容也能补发”。

建议在 UI 中明确提供选择：

- 仅对新内容生效。
- 对历史内容补建队列。
- 只补建最近 N 天或匹配某些标签的内容。

### 4. 后处理失败未充分反馈给前端

解析成功后还会触发摘要、Embedding、巡逻评分、分发等后处理。即使主解析成功，后处理仍可能失败。当前这些失败更偏后台诊断信息，不一定进入用户当前操作反馈。

建议内容详情页展示后处理状态：

- 摘要：未配置/生成中/成功/失败。
- 语义索引：未入库/排队中/成功/失败。
- 分发：未匹配规则/已入队/待审核/已推送/失败。

## 测试可信度

最近验证结果：

| 后端非 integration | `.venv\Scripts\python.exe -m pytest backend/tests -q -m "not integration" --no-cov` | 670 passed, 4 skipped, 16 deselected | 本地核心逻辑较稳 |
| 后端 integration | `.venv\Scripts\python.exe -m pytest backend/tests -q -m integration --no-cov` | 5 failed, 8 passed, 1 skipped, 2 xfailed | 真实平台/真实外部服务链路不稳 |
| 前端静态检查 | `flutter analyze` | No issues found | Dart/Flutter 静态检查通过 |
| 前端测试 | `flutter test` | 21 tests passed | 基础 widget/unit 测试通过，但覆盖有限 |

integration 失败主要集中在真实知乎/小红书内容解析和真实 LLM 调用路径，存在 403、安全校验、连接失败或 cwd 依赖导致 skip 的问题。这说明当前离线单元测试可信，但真实平台功能还不能只靠现有测试证明稳定。

建议新增产品级验收脚本或清单：

1. 添加普通 URL，确认收藏库出现、解析状态成功、摘要/封面/标签生成。
2. 添加知乎/小红书 URL，确认登录态有效时能解析，失效时错误可理解。
3. 配置 RSS 发现源，手动同步，确认发现列表出现新条目。
4. 配置一个分发目标和规则，确认审核后只影响预期目标。
5. 启用收藏同步，手动触发一次，确认同步数量、失败数量、重复处理和最近同步时间。
6. 故意填错 LLM key 或断开平台登录，确认 UI 能指出具体失败原因。

## 安全扫描汇总

安全扫描报告位于 `.codex-security-scans/VaultStream/1a616d81_20260530T145418_ws/report.md`。扫描方式是 repository-wide Deep Security Scan，包含深度发现、集中验证和攻击路径分析。报告明确说明未运行生产部署、外部网络探测或完整后端端到端服务。

扫描结果：

| 指标 | 结果 |
| --- | --- |
| 可报告发现 | 8 |
| 严重性 | high=1, medium=6, low=1 |
| 置信度 | high=5, medium=3 |
| 验证方式 | 静态追踪和有限本地路径模拟 |

### S1. Release 构建把后端 API token 嵌入客户端产物

- 严重性：high
- 置信度：high
- 影响：如果 GitHub Actions 手动构建把 `secrets.API_TOKEN` 通过 `--dart-define=API_TOKEN` 注入 Flutter web/APK，分发产物中可能包含可恢复的后端共享 token。
- 风险：任何拿到产物的人可能提取 token 并调用受保护后端 API。
- 建议：停止在分发构建中注入后端共享 token；改为用户级或短期 token；如曾发布相关产物，应轮换 token；CI 增加禁止规则。

### S2. 归档媒体处理缺少 SSRF 控制

- 严重性：medium
- 置信度：high
- 影响：RSS、发现源或通用解析可以带入图片/视频 URL，媒体处理器会用 httpx 跟随重定向下载，缺少私网、link-local、redirect 最终目标校验。
- 建议：所有服务端 URL 获取统一走 SSRF-safe fetcher，校验 scheme、DNS、连接目标、重定向、大小和内容类型。

### S3. Browser-auth 路由缺少 API token 保护

- 严重性：medium
- 置信度：high
- 影响：`/api/v1/browser-auth` 下的会话创建、状态检查、登出、Cookie 刷新等路由未强制 API token，可能被可访问后端的网络客户端滥用，造成凭据状态篡改或登录流程干扰。
- 建议：在 router include 或 APIRouter 层添加 `Depends(require_api_token)`，并增加缺失/错误 token 的回归测试。

### S4. 公开图片代理只做连接前 DNS 校验

- 严重性：medium
- 置信度：medium
- 影响：图片代理会预解析 DNS 并拒绝私网地址，但实际 httpx 连接仍使用原始 hostname，没有绑定已校验 IP，理论上存在 DNS rebinding 或解析差异绕过。
- 建议：连接时绑定或验证目标 IP；每次重定向后重新校验；禁止私网、link-local、reserved 目标。

### S5. 公开媒体路由使用不安全字符串前缀路径检查

- 严重性：medium
- 置信度：medium
- 影响：Windows 路径下，`realpath(file).startswith(realpath(root))` 可能把 sibling-prefix 路径误判为在存储根目录内。
- 建议：拒绝 absolute/rooted key；使用 `Path.resolve()` 和 `relative_to()` 做真实祖先关系校验；补 Windows 编码分隔符、盘符、大小写测试。

### S6. Telegram bot 白名单默认允许所有用户

- 严重性：medium
- 置信度：high
- 影响：白名单为空时当前逻辑等价 allow-all。启用 bot 后，未列入黑名单的任意 Telegram 用户可能调用命令，甚至通过 `/ai` 进入 Agent 执行。
- 建议：生产环境无白名单时 fail closed；如确需公开 bot，使用显式 `ALLOW_ALL_TELEGRAM_USERS=true`；启动时给出阻断或强警告。

### S7. 通用分享解析可触发内部 URL 获取

- 严重性：medium
- 置信度：high
- 影响：持有 API token 的客户端可以提交任意 URL，unknown host 会进入 universal adapter，`tiered_fetch` 使用 httpx/Playwright 直接获取，缺少统一 SSRF 策略。
- 建议：通用解析和 Playwright navigation 也必须走 SSRF-safe fetcher/策略；对 localhost、RFC1918、metadata、redirect 加测试。

### S8. 本地归档媒体可无鉴权访问

- 严重性：low
- 置信度：medium
- 影响：内容展示会把本地归档媒体改写为 `/api/v1/media/...`，而媒体路由/静态挂载不要求 API token。若媒体 key 泄露，可能绕过内容 API 的鉴权边界。
- 建议：使用短期签名 URL 或媒体路由鉴权；避免私有归档存储直接被 unauthenticated StaticFiles 暴露。

## 综合优先级

### P0：先修影响安全和用户信任的基础问题

- 禁止 release/manual 分发构建注入后端 API token，并轮换可能泄露的 token。
- 给 browser-auth 路由加 API token 保护。
- 建立统一任务运行记录，至少覆盖收藏同步、发现同步、解析、摘要、Embedding、分发。
- 分发队列前端默认改用 `queue_item_id` 级操作，content-level 操作必须显示影响范围。

### P1：收敛自动化链路

- 把收藏同步升级为可追踪、可预览、可重试的独立功能。
- 建立账号与平台健康中心。
- 所有服务端 URL 获取统一 SSRF 防护，包括媒体处理、图片代理、通用解析和 Playwright。
- 明确发现源支持边界：当前已按 RSS 和 Telegram Channel 收敛；后续新增来源必须端到端补齐 scraper、API 和 UI。

### P2：提升产品可理解性

- 将 LLM 配置改为能力状态优先。
- 内容详情页显示摘要、语义索引、分发等后处理状态。
- 错误提示从底层异常改为用户可行动的分类。
- 新增目标时提供历史内容补建队列选项。
