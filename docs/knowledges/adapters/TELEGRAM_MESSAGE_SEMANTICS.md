# Telegram 消息关系与订阅适配依据

2026-09-25：官方协议研究及当前代码核对；原生读取层已实现，调度与入库尚在接入；未读取用户账号的私有消息。用户要求先理解消息逻辑，再实施账号订阅及收藏接入。

## 两种用户意图

- 选定频道、群组的订阅内容进入动态候选池，按兴趣去重、聚合、评分和清理。
- Saved Messages 是主动收藏，直接进入收藏库，不以兴趣低分拒收，也不受候选 TTL 清理。
- 默认自动选择已加入且有效通知开启的频道；用户显式停用的来源不能被下次频道枚举重新启用。

## 协议事实与对应取舍

| 场景 | Telegram 提供的依据 | 适配取舍 |
| --- | --- | --- |
| 消息身份 | `peer_id`、`id`；频道／超级群的消息 ID 属于各自会话 | 接入身份使用账号、带类型的 peer ID、消息 ID；用户名和公开 URL 只作访问入口，不能作唯一身份 |
| 频道原生转发 | `fwd_from.from_id`、`channel_post`、`date` 等字段 | 字段充分时建立明确的原帖关系；同时保留当前会话的消息身份与转发时间 |
| 收藏转发内容 | `saved_from_peer`、`saved_from_msg_id`，以及可选 `saved_from_id`、`saved_date` | 区分最初来源、收藏时所在会话和收藏时间；不可把 saved_from 字段套用到所有普通转发 |
| 隐藏来源／复制重发 | 可能只有 `from_name` 或完全没有转发头 | 不凭昵称认定作者身份，不假造来源链；内容指纹只证明载荷重复，不能证明谁原创 |
| 回复、局部引用、跨会话引用 | `reply_to_msg_id`、`reply_to_peer_id`、`quote_text`、`reply_from` 等 | 引用内容与当前消息自身正文分别保存；关联不等于重复，不吞掉新增观点 |
| 频道关联讨论组 | 频道帖子自动转发到讨论组，其消息线程承载评论 | 自动转发与频道原帖可关联折叠；评论是独立内容，保留线程及回复关系 |
| 相册／媒体组 | 多条消息共享 `grouped_id`，各自仍有消息 ID | 按会话内媒体组组装展示；跨分页／事件到达分批时继续补齐，不把第一张当完整相册；跨频道转发按成员来源比较，不能只比 grouped_id |
| 内容更新 | 消息编辑／删除更新，`pts` 等更新状态及 difference 补齐机制 | 新消息水位与编辑删除更新分别处理；消息 ID 缺口不是丢消息证明，历史回填游标也不能替代更新状态 |
| 媒体定位 | 媒体 ID、access hash、可能过期的 file_reference | 保留可重新取得文件引用的消息定位；过期后重取消息。文件字节下载后复用现有哈希存储和节省空间的转码流程 |

来源字段不是完整转发路径列表，但可以沿可定位的上游消息继续读取并串联已确认关系。对于原帖不可访问的转发，保留已读到的副本及已知关系，不要求原帖抓取成功才允许入库。来源隐藏、删除、无权限或缺少定位时，前端按无来源处理，省略来源展示，不增加断点、待溯源或访问失败等调试标签；技术原因只用于内部诊断。

## 去重、评分与聚合

1. 同一个远端消息重复同步：更新已有记录，避免追加重复来源或重复执行后处理。
2. 同一原帖的多个等价转发：动态中折叠展示，同时保留各频道出现记录。载荷不一致时保留差异，不因原帖 ID 相同而覆盖正文或媒体。
3. 没有来源头的完全相同内容：结合正文、链接实体和媒体身份判断重复；不能仅凭相同链接、短文案或相同图片判定整条重复。
4. 引用并补充评论、同题不同报道：保留独立内容，再按具体事件聚合。原生去重不调用模型，事件归并才按需使用已有聚合能力。
5. 转发数量不等于独立证据数量。重复副本复用适用的分析结果；用户兴趣、评分规则或正文版本变化时重新判断。来源偏好可影响展示排序，不让跨频道转发循环自动抬高可信度或触发重复推送。
6. 相同内容被主动收藏时增加收藏归属并复用资产。取消某个来源或删除某条远端副本，不应自动删掉其他来源仍引用的内容；取消收藏行为沿项目用户可见策略处理。

这是内容身份与来源记录的职责划分，不要求新建多套正文、媒体或模型处理管线。实施时先确定现有表能表达的关系，再补确有需要的消息映射。

## 当前实现的具体缺口

- `adapters/telegram.py` 读取公开 HTML：正文、媒体和 `quoted_content`，没有原生转发身份、完整线程或账号更新状态。
- `tasks/discovery_sync.py` 按 canonical URL 查重；不同频道转发 URL 不同，无法据此识别同一原帖。新候选目前统一写入 `Platform.UNIVERSAL`，接入原生消息时需保留真实平台身份。
- `ContentDiscoveryLink` 每内容／发现源唯一，不能直接表达同一来源重复转发的多个消息；不可把“所属订阅源”和“远端消息出现记录”混为一件事。
- 现有自动聚合是默认关闭的模型综合稿工作流，不承担 Telegram 原生去重，不能用它代替转发关系识别。
- 收藏 fetcher 以 URL 为主；原生文字和附件需复用文本／文件捕获能力，不能伪造公开 URL 再发到网页解析器。

## 本次接入验证（2026-09-25）

- Telegram 官方应用申请说明没有 Premium 前置要求，API 免费开放。应用 api_id/api_hash 属于开发者，登录用户不必各自申请。
- 官网申请表的 Short name 仅允许字母数字，长度 5–32。修正格式并补全信息后仍返回通用 ERROR；不能据此断言具体是号码或 IP 风控。
- 用户随后确认之前使用了错误的扫码入口，改正后已登录官方 Web K；浏览器页面也已确认登录。因此此前扫码失败不能作为账号、网络或应用凭据受限的证据。应用注册仍失败，是独立问题。
- 使用正确入口扫描本地自动刷新二维码后，原生会话已授权，且确认账号为用户指定账号。使用官方 TEST ONLY 应用凭据，仅限本地验证，不能作为部署凭据。
- 真实只读验收：124 个已加入广播频道，其中 77 个按有效通知设置开启通知；抽查 3 个频道各 20 条消息，分别组装为 20、18、20 篇内容，其中第二个频道合并了 2 个相册。Saved Messages 读取 20 条，其中 19 条转发；抽查其中 3 条均解析出一层可访问来源。频道样本的一条转发也解析出一层来源。未发送消息或改变已读状态。
- 本次证明原生登录、通知筛选和消息读取可用；尚不代表真实账号入库、媒体归档、评分、推送或服务器长期同步已经验收。正式运行仍需有效的非测试应用凭据。

## 原生读取层

用户指定频道首次只补接入前 24 小时的动态，随后按消息游标增量同步；首次窗口以来源创建时间固定，按时间正序每批 100 条，避免高频频道截断中间消息。窗口内无消息时记录频道最新消息编号，不在下一轮回退到全历史。Saved Messages 独立从最早收藏开始逐批补齐。

真实接入发现部分图片只有内嵌缓存尺寸；直接 iter_download 会错误地发起远端文件请求，返回 FileReferenceExpiredError，刷新引用也无效。图片使用 Telethon download_media 选择有效尺寸并解码内嵌图片，再进入统一 WebP 存储；其他媒体继续流式下载，遇到真正过期的引用时从原消息刷新并续传。

`adapters/telegram_account.py` 使用 Telethon 1.45：频道枚举读取全局 Broadcasts 默认及会话 mute_until；分页初次取近期、后续从游标向新消息读取，页末相册继续读完。正文经 Telegram 实体转为 Markdown；指纹排除计数和临时文件引用；可定位转发沿上游读取，缺少来源时不产生用户诊断标签。

`telegram_messages` 按账号、带类型的会话 ID 和消息 ID 记录出现位置。它不代替 ContentSource，不让普通频道同步永久保护候选。Saved Messages 后续入库才建立永久收藏来源。

一次性协议样本覆盖相册跨页、增量积压、最新页、转发载荷、来源链和通知默认继承；并非真实账号验收。新库建表和从前一 revision 的增量迁移通过。早期服务器快照未受 Alembic 管理，不能用于直接升级验证，未对它强行盖版本。

原生同步每轮额外按持久游标回查 20 条已收录内容，按完整本地消息组取得当前正文和媒体，覆盖较早编辑和归档策略改变后的补齐。回查游标在该批入库成功后前进，走到末尾后重置；不是实时 updates 订阅。远端消息已删除时保留本地存档，不反向删除收藏，也不添加前端诊断标签。

原生 reply_to.quote_text 使用现有 rich_payload.quoted_content 展示，与消息本身的评论正文分开；没有引用片段时不猜测上游正文，也不添加空引用区块。
